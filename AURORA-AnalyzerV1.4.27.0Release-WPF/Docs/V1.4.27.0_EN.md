## 1. Version Overview

V1.4.27.0 represents the most significant architectural upgrade of AURORA-Analyzer since the project's inception. The entire user interface layer has been migrated from the traditional model of directly creating WinForms GDI+ controls via PowerShell scripts to the Windows Presentation Foundation framework. This migration is not a simple technology stack swap; it encompasses a comprehensive refactoring across five dimensions: the rendering pipeline, event model, control lifecycle, resource management strategy, and animation system.

In V1.3.26.7 and earlier versions, the core architecture relied on PowerShell scripts dynamically compiling C# Windows.Forms classes through Add-Type to create UI controls, with all rendering performed by GDI+ on the CPU. This approach provided the advantage of rapid prototyping during the early stages of the project, but as UI complexity grew—frosted glass backgrounds, starfield particles, 17 button animation effects, UWP-style view transitions—the CPU rendering bottleneck of GDI+ and the single-threaded STA message pump model of WinForms became the performance ceiling.

V1.4.27.0 replaces the UI layer entirely with a C# 5.0 compiled WPF control library, leveraging WPF's retained-mode rendering pipeline, GPU-accelerated DirectX backend, data-binding-driven MVVM architecture, and a dual-drive animation system powered by Storyboard and CompositionTarget.Rendering. The result is a several-fold improvement in rendering performance and a clearly layered code architecture.

Despite the fundamental changes in the underlying rendering engine, V1.4.27.0 maintains complete compatibility with the V1.3.x series in terms of PowerShell script interfaces, the syncHash synchronization mechanism, command-line arguments, and business logic workflows. Existing PowerShell script engines can run on the new architecture without any modifications.

## 2. Architecture Changes

The architecture changes in V1.4.27.0 span five core dimensions, each representing a fundamental shift from the old paradigm to the new.

### 2.1 Event Model: From WinForms Event-Driven to WPF MVVM Pattern

In V1.3.x, UI interaction logic was directly embedded in PowerShell scripts, with event handlers registered via `$Button.Add_Click({ ... })`. Business logic and UI code were tightly coupled—a single script could simultaneously contain database query logic and button color configuration code. This made unit testing nearly impossible and code reuse extremely low.

V1.4.27.0 introduces the MVVM architecture, completely decoupling UI interaction logic from business logic. ViewModels expose bindable properties and commands by implementing the INotifyPropertyChanged interface, while the View layer is responsible solely for declaratively binding to these properties, containing no business logic whatsoever. The Service layer encapsulates all business operations, and ViewModels obtain Service instances through dependency injection, further reducing coupling.

### 2.2 Control Creation: From PowerShell Script-Created UI to C# 5.0 Compiled Control Library

In V1.3.x, all UI controls were created by dynamically compiling C# code at runtime through PowerShell's Add-Type. Under this approach, all control classes had to be recompiled on every startup, with startup time growing linearly with the number of controls. Furthermore, Add-Type-compiled code could not use NuGet packages, could not benefit from pre-compilation optimizations, and could not leverage IDE features such as IntelliSense and refactoring support.

V1.4.27.0 extracts all UI controls into an independent C# 5.0 class library project, pre-compiled into a DLL. At startup, the pre-compiled assemblies are loaded directly, significantly reducing startup time. The control library is developed in Visual Studio, enjoying full IntelliSense, static analysis, and refactoring tool support. The C# 5.0 language version was chosen to maintain compatibility with PowerShell 5.1, ensuring that compiled DLLs can be loaded within the PowerShell 5.1 CLR environment.

### 2.3 Parallelism Model: From Single Runspace to RunspacePool Parallelism

V1.3.x used a single PowerShell Runspace to execute all background tasks. When a background task was performing a long-running operation, the UI thread could experience stuttering while waiting for syncHash synchronization.

V1.4.27.0 introduces the RunspacePool parallel model. The PowerShellHost Service manages a RunspacePool with the maximum concurrency dynamically adjusted based on the current performance tier. Each background task acquires an independent Runspace from the pool, and the Runspace is returned to the pool for reuse upon task completion. The UI thread communicates with Runspaces through syncHash, completely avoiding blocking of the WPF rendering thread.

### 2.4 Rendering Pipeline: From GDI+ CPU Rendering to WPF GPU-Accelerated Rendering

This is the most fundamental source of performance improvement. GDI+ performs all 2D drawing operations—including anti-aliasing, transparency blending, and gradient fills—on the CPU. When the UI contains numerous semi-transparent effects, blurred backgrounds, and particle animations, the frame rate of CPU rendering drops sharply.

WPF's rendering pipeline is built on DirectX 9/11, with all drawing operations executed by the GPU. This means that extensive semi-transparent layering, Gaussian blur, gradient fills, and similar operations can be processed in parallel on the GPU, freeing CPU resources for business logic computation. In V1.4.27.0, the real-time blur of frosted glass backgrounds, 60fps rendering of starfield particles, gradient animation effects on buttons, and more are all GPU-accelerated, resulting in a significant reduction in CPU utilization.

### 2.5 Language Engine: From Dual Language Engine Files to Single Engine + LanguageService

V1.3.x used two separate engine files, CHSPRO and ENGPRO, to support Chinese and English language switching. This meant that every modification to the engine logic had to be synchronized across both files, incurring high maintenance costs and making behavioral inconsistencies between the Chinese and English versions easy to introduce.

V1.4.27.0 merges the engine files into a single engine, with all UI text dynamically switched at runtime through the LanguageService. The LanguageService maintains a resource dictionary where each text key corresponds to both a Chinese and an English value. WPF's DynamicResource mechanism ensures that all bound UI text updates automatically when the language is switched, without requiring an application restart.

## 3. MVVM Architecture

The MVVM architecture in V1.4.27.0 is divided into four clearly defined layers, each with explicit responsibility boundaries.

### 3.1 View Layer

The View layer consists of four WPF Windows/UserControls, responsible for purely declarative UI layout and style definitions.

| View | Type | Responsibility |
|------|------|------|
| SplashScreenView | Window | Startup splash screen, displaying loading progress and an irregular transparent window |
| MainFormView | Window | Main interface, containing the button panel, console output, starfield background, and frosted glass effect |
| ProModeView | Window | Pro mode panel, providing entry points for advanced diagnostic features |
| UndoViewerView | Window | Undo viewer, displaying historical operation records and rollback options |

Each View's XAML file contains only control declarations, style bindings, and animation trigger definitions, with no business logic code whatsoever. Views bind to their corresponding ViewModels through DataContext, and all interactions are implemented through Command bindings and Data Binding.

### 3.2 ViewModel Layer

The ViewModel layer serves as the bridge between Views and Services, responsible for transforming Service-layer business data into a format directly bindable by the View layer.

Each ViewModel implements the INotifyPropertyChanged interface, automatically notifying the View to update when property values change. All ViewModels inherit from a unified ViewModelBase base class, which encapsulates the PropertyChanged event triggering logic and simplified property change invocation.

Navigation between ViewModels is implemented through the NavigatorService, with support for animation choreography during view transitions. ViewModels do not directly reference View instances; instead, they request view transitions through the NavigatorService, maintaining complete decoupling between Views and ViewModels.

### 3.3 Service Layer

The Service layer is the core carrier of business logic, comprising 14 independent service classes, each encapsulating a single-responsibility business domain.

| Service | Responsibility |
|------|------|
| PowerShellHost | Manages the RunspacePool, executes PowerShell scripts, communicates with the UI thread via syncHash |
| RenderEngine | Encapsulates low-level operations of the WPF rendering pipeline, manages CompositionTarget rendering events |
| ElevationService | Handles UAC elevation requests, manages generation and verification of elevation tokens |
| SecurityService | Drives integrity verification and token validation workflows |
| LanguageService | Manages multilingual resource dictionaries, dynamically switches language at runtime |
| NavigatorService | Manages navigation between Views, choreographs view transition animations |
| AnimationService | Coordinates the starting, stopping, and status querying of Storyboard and frame-level animations |
| ThemeService | Manages application themes, provides aurora color sampling and breathing modulation |
| SettingsService | Persists and reads user configuration, including performance tier settings |
| TelemetryService | Structured telemetry data recording, persistence, and reporting |
| SessionService | Session state saving and restoration, including AgeInDays tracking |
| WatchdogService | Watchdog monitoring, detects abnormal process exits and triggers secure cleanup |
| IntegrityGuardService | Integrity verification, detects file tampering and unauthorized modifications |
| LogService | Structured log output, supporting tiered filtering and file persistence |

### 3.4 Animation Layer

The Animation layer is a fourth layer added in V1.4.27.0 beyond the standard MVVM layers, specifically dedicated to handling complex UI animation logic.

| Component | Responsibility |
|------|------|
| AnimationHelper | Provides animation utility methods such as easing function lookup, animation state queries, and frame-rate normalization calculations |
| UwpEasingCurves | Implements UWP-style easing curves (CubicEase, BackEase, CircleEase, etc.) for use by Storyboard |
| AuroraCustomEasing | Implements Aurora custom easing curves, including iOS-style double-bounce curves and breathing-style easing |

## 4. Frosted Glass Material System

AuroraGlassMaterial is the most complex visual system in V1.4.27.0, implementing a high-performance frosted glass effect through a four-layer rendering pipeline. The design goal of this system is to visually present the translucency and depth perception consistent with the Windows Acrylic material, while not dragging down the overall rendering frame rate in terms of performance.

### 4.1 Four-Layer Rendering Pipeline

The frosted glass effect is achieved through four stacked layers, from bottom to top:

The first layer is a dual drop shadow. The bottom shadow uses a large-radius soft shadow to simulate the light bloom diffusion of glass material, while the top shadow uses a small-radius sharp shadow to enhance the three-dimensionality of the glass edges. The colors and opacity of both shadows are dynamically adjusted based on the current aurora theme color, ensuring the glass material coordinates tonally with the overall UI.

The second layer is the true blurred background. This is the core of the frosted glass effect. The system captures the visual content behind the glass control using RenderTargetBitmap, then applies a GaussianBlurEffect for blurring, and finally uses the blurred result as the background fill. The blur radius ranges from 12 to 24 pixels, dynamically adjusted based on window size to ensure appropriate blur levels at different resolutions.

The third layer is the glass body gradient. A semi-transparent linear gradient is overlaid on top of the blurred background to simulate the light refraction effect of glass material. The start and end colors and opacity of the gradient are dynamically sampled from the aurora theme color, causing the glass material to present different hues as the theme color changes.

The fourth layer is the surface overlay. The topmost layer is a subtle noise texture overlay used to simulate the grainy feel of frosted glass. The noise texture is generated using a fixed seed at 128×128 pixels, ensuring a consistent noise pattern across startups without flickering.

### 4.2 30fps Blur Capture Throttling

The biggest performance bottleneck for real-time blurred backgrounds is the RenderTargetBitmap capture operation, which requires rendering the entire visual tree into a bitmap. If performed every frame, even if the GPU could handle it, memory bandwidth would become the bottleneck.

V1.4.27.0 implements an intelligent throttling mechanism: the blurred background is captured and updated at a fixed frequency of 30fps, rather than following WPF's 60fps rendering loop. This means the blur capture frequency is halved, with virtually no perceptible difference in visual effect—since the blurred background itself changes relatively slowly. More importantly, when no frosted glass controls are visible in the window, the system completely skips the RenderTargetBitmap capture operation, releasing all saved resources to other rendering tasks.

### 4.3 Brush Cache Pool

Frequent creation of gradient brushes and color brushes in WPF triggers substantial managed heap allocations and small object collections, increasing GC pressure. V1.4.27.0 introduces a brush cache pool mechanism: all commonly used gradient and color brushes are frozen to immutable objects via the Freeze method immediately after their first creation and cached in a dictionary. Subsequent usage retrieves them directly from the cache pool without requiring new memory allocations.

Once frozen, brush objects enter the Frozen state, allowing the WPF rendering engine to apply special optimizations—since immutable objects require no thread synchronization, no cloning, and can be shared directly in GPU memory. This means that during each frame's rendering process, all brush operations of the frosted glass system are zero-GC-allocation.

### 4.4 Micro-Noise Texture

The grainy feel of frosted glass is achieved through a 128×128 pixel micro-noise texture. The texture is generated using a fixed seed, ensuring a consistent noise pattern across startups. All frosted glass controls share the same noise texture instance—initialized via Lazy pattern, created on first access, and then referenced by all controls as a single instance. This avoids the memory waste of repeatedly generating noise textures for each glass control.

The noise texture is overlaid on the glass body at extremely low opacity, with the subtle grainy texture only perceptible upon close observation. This level of detail is one of the core elements of the Aurora visual design language, which was impossible to achieve in the V1.3.x era due to GDI+ performance limitations.

## 5. Starfield Background

AuroraStarfield is the starfield particle system for the main interface background, which in V1.4.27.0 has been fully migrated from GDI+ CPU per-pixel rendering to WPF GPU-accelerated rendering.

### 5.1 CompositionTarget.Rendering 60fps VSync-Driven

The starfield system uses WPF's CompositionTarget.Rendering event to drive per-frame updates. This event fires on each vertical sync signal, synchronized with the display refresh rate. On a 60Hz monitor, this is 60fps; on a 120Hz monitor, 120fps. The actual computation of frame updates—particle position updates, color interpolation, new particle generation—is performed on the CPU, but all drawing operations—dot rendering of particles, transparency blending, glow effects—are processed in parallel by the GPU.

### 5.2 Frame-Rate Normalization

Moving particles by a fixed step size on each frame directly would cause a problem: on a 120Hz monitor, particles would move twice as fast as on a 60Hz monitor, causing animation fast-forward. V1.4.27.0 uses `Stopwatch` to measure the actual frame interval and performs frame-rate normalization against a 30fps baseline. All time-dependent calculations—particle displacement, color gradients, opacity decay—are multiplied by a normalization factor of `deltaTime / (1.0 / 30.0)`, ensuring that the perceived animation speed is completely consistent across displays with different refresh rates.

### 5.3 Pre-Generated Aurora Brush Cache Pool

The aurora particles in the starfield use RadialGradientBrush to achieve a gradient effect from bright white at the center to transparent at the edges. Similar to the brush cache of the frosted glass system, all aurora brushes are frozen and cached after first creation. The cache pool is organized by particle type (stars, planets, meteors, aurora bands) and color scheme (blue-green, purple-pink, cyan-blue), allowing fast lookup by index at runtime.

### 5.4 Real-Time-Step-Driven

Particle motion calculations use the real time steps obtained from `Stopwatch`, rather than relying on frame count. This means that even if a particular frame is delayed due to UI thread busyness, the particle positions in the next frame will be calculated based on the actual elapsed time, covering the skipped movement distance. This is completely decoupled from the rendering frame rate, ensuring the temporal accuracy of the animation.

## 6. Button System

AuroraButton is the most heavily customized control in V1.4.27.0, fully preserving the 17 animation effect details accumulated during the V1.3.x era and undergoing GPU-accelerated refactoring in WPF.

### 6.1 17 Animation Effect Details

The button's 17 animation effects are implemented through WPF's Trigger and VisualState mechanisms, covering visual changes across six states: normal, hover, press, release, disabled, and focused. These effects include: background gradient offset on hover, border glow spread, text shadow appearance, icon micro-scaling, inner shadow deepening, outer glow diffusion, background compression on press, border contraction, text sinking, icon shrinking, inner shadow flattening, elastic recovery on release, background bounce-back, border bounce-back, text bounce-back, icon bounce-back, and outer glow dissipation.

In V1.3.x, these effects were implemented through multiple WinForms Timers and GDI+ per-frame rendering, requiring a full redraw of all button pixels per frame. In V1.4.27.0, these effects are implemented through WPF's Storyboard and property animations, with the GPU processing only the changed pixel regions, resulting in significant performance improvement.

### 6.2 Aurora Ambient Color Injection

The button's background gradient and border glow colors are not fixed; instead, they are sampled from the aurora color band based on the button's Y-axis coordinate position within the window. The aurora color band is a vertical gradient spectrum transitioning from purple-blue at the top to cyan-green at the bottom. The button's Y coordinate is mapped to the corresponding position on the color band, sampling the RGB color value at that position as the base color for the button's ambient color.

Furthermore, the ambient color is overlaid with a breathing modulation effect. The breathing cycle is approximately 4 seconds, using a sine wave function to modulate the color brightness, causing the button color to periodically brighten and dim within a subtle range, simulating the visual effect of flowing aurora bands. This level of detail makes the buttons appear immersed in a real aurora environment rather than simply having a static gradient overlaid on them.

### 6.3 iOS Bouncy Release Feedback

The rebound animation on button release uses an iOS-style double-bounce curve. When the user releases the button, the button first continues to compress slightly further in the press direction (simulating inertia), then rebounds to a size slightly larger than the original (overshoot), then rebounds again to a size slightly smaller than the original (secondary overshoot), and finally settles at the original size. The entire rebound process lasts approximately 600ms and is implemented through a custom AuroraCustomEasing curve.

In WPF, this complex bounce curve is implemented by inheriting the IEasingFunction interface to create a custom easing function, which is then referenced directly in the Storyboard's DoubleAnimation. Compared to the multi-Timer segmented implementation in V1.3.x, the WPF implementation is cleaner, more precise, and does not depend on Timer accuracy.

### 6.4 Micro-Noise Frosted Texture

The button surface is overlaid with a micro-noise frosted texture, using the same generation algorithm and sharing mechanism as the frosted glass system's noise texture. The noise texture is shared as a single instance across all buttons via Lazy pattern, ensuring zero additional memory overhead.

## 7. Animation System

The animation system in V1.4.27.0 represents the most profound architectural transformation in the project's animation domain. Moving from the WinForms Timer-driven segmented animation of V1.3.x to a dual-drive architecture combining Storyboard window-level animation and CompositionTarget.Rendering frame-level animation.

### 7.1 Four-Phase View Transition

View transition animations are divided into four precisely choreographed phases, with the duration of each phase calculated precisely to ensure visual fluidity.

Phase one, button exit. All buttons in the current view execute exit animations, fading out and sinking in sequence from bottom to top, with a 40ms delay stagger between each button, creating a ripple exit effect. The total duration of phase one depends on the number of buttons, typically ranging from 200ms to 350ms.

Phase two, skeleton exit. The skeleton elements of the current view—such as the window background and panel frames—execute a unified fade-out and shrink animation, lasting 200ms.

Phase three, skeleton entry. The skeleton elements of the target view—such as the window background and panel frames—execute a unified fade-in and expand animation, lasting 250ms. The skeleton entry is slightly longer than the skeleton exit because the entry animation requires more time for the user to perceive the spatial structure of the new view.

Phase four, button entry. All buttons in the target view execute entry animations, fading in and floating up in sequence from top to bottom, likewise with a 40ms delay stagger between each button, creating a ripple entry effect. The total duration of phase four depends on the number of buttons, typically ranging from 200ms to 350ms.

The total duration of the entire four phases ranges from approximately 850ms to 1150ms, consistent with the natural transition time window of human visual perception.

### 7.2 Dual-Drive Architecture

The dual-drive architecture is the core design decision of the animation system in V1.4.27.0.

Storyboard drives window-level animations, including view transitions, button state transitions, console scrolling, and more. Storyboard's advantages lie in its declarative definition, automatic timeline management, built-in easing function support, and the native optimization that the WPF framework provides for Storyboard.

CompositionTarget.Rendering drives frame-level animations, including starfield particle updates, aurora color band flow, breathing modulation, and more. Frame-level animations require updating properties on every frame, a scenario that Storyboard cannot handle efficiently. CompositionTarget.Rendering fires on each vertical sync signal, and combined with the frame-rate normalization algorithm, ensures that frame-level animations maintain consistent perceived speed across different refresh rates.

Both driving approaches are coordinated through the AnimationService. The AnimationService ensures that the same property is not modified by both driving approaches simultaneously, avoiding animation conflicts. During view transitions, the AnimationService temporarily pauses frame-level animations driven by CompositionTarget.Rendering, prioritizing the fluidity of the view transition animation.

### 7.3 UWP-Style Easing Curves

V1.4.27.0 implements a complete library of UWP-style easing curves, including CubicEase, QuadraticEase, QuarticEase, QuinticEase, SineEase, CircleEase, BackEase, ElasticEase, BounceEase, and PowerEase—10 easing functions in total. Each easing function supports three modes: EaseIn, EaseOut, and EaseInOut, uniformly exposed through the UwpEasingCurves class.

These easing curves are widely used in UWP and Windows 11 native applications. Their introduction ensures that the animation feel of Aurora is consistent with Windows native applications, eliminating the previous GDI+ animation sensation of being "non-linear but not quite natural."

## 8. Console

AuroraConsoleBox is the log output console at the bottom of the main interface, which has undergone a comprehensive WPF refactoring in V1.4.27.0.

### 8.1 Batch Line Refresh

In V1.3.x, the console refreshed the display immediately upon receiving each log entry. When log output frequency was high, frequent UI updates caused interface stuttering. V1.4.27.0 introduces a batch line refresh mechanism: log lines first enter a buffer, and after a 320ms batch delay, all accumulated log lines in the buffer are output to the UI in a single operation.

During this 320ms batch delay period, the system also executes a 260ms smooth scrolling animation. The console scrollbar does not jump directly to the new position; instead, it smoothly scrolls to the bottom using a UWP-style easing curve, avoiding abrupt jolts.

### 8.2 UWP-Style Text Slide-In Animation

When each new log line appears, it is not simply displayed directly; instead, it executes a slide-in animation from the right. The text starts from a 20-pixel offset on the right, slides into its normal position over 200ms, while simultaneously transitioning opacity from 0 to 100%. When multiple log lines appear simultaneously, each line has a 30ms delay stagger, creating a cascading line-by-line slide-in effect.

### 8.3 Frosted Glass Background and Custom Scrollbar

The console background adopts the frosted glass effect of AuroraGlassMaterial, maintaining visual consistency with the main interface. The scrollbar is fully custom-drawn, using the aurora theme color as the thumb color, with the track rendered as semi-transparent glass material. The custom scrollbar expands to normal width on mouse hover and contracts to a thin strip mode when the mouse leaves, balancing aesthetics and usability.

## 9. Performance Optimization

The performance optimization strategy of V1.4.27.0 revolves around three core objectives: reducing CPU rendering load, lowering GC pressure, and avoiding unnecessary rendering operations.

### 9.1 Four-Tier Performance Levels

The system provides four performance tiers, allowing users to freely choose based on their hardware configuration.

| Tier | Name | Target FPS | Blur Quality | Particle Count | Animation Complexity | Applicable Scenario |
|------|------|------------|--------------|----------------|----------------------|---------------------|
| 1 | Eco | 30fps | Low (8px radius) | 50% | Simplified | Low-end machines, virtual machines |
| 2 | Balanced | 60fps | Medium (16px radius) | 75% | Standard | Standard office computers |
| 3 | Performance | 60fps | High (24px radius) | 100% | Full | High-performance laptops |
| 4 | Extreme | 120fps | Maximum (32px radius) | 150% | Full | High-end desktops, gaming laptops |

In Eco mode, the blur background capture frequency is reduced to 15fps, the blur radius is reduced to 8px, the starfield particle count is reduced by 50%, and some non-critical button animation effects are simplified. In Extreme mode, all effects run at maximum quality, the blur capture frequency is increased to 60fps, and the starfield particle count is increased to 150% of the baseline.

### 9.2 Brush Cache Pooling

As described in the frosted glass system, all commonly used brushes are frozen and cached after first creation. This optimization is particularly effective in frequently rendered scenarios—a view containing 10 buttons may involve 50 or more brush references per frame, and cache pooling transforms these operations from "allocate a new object each time" to "look up a frozen object from the dictionary," completely eliminating the corresponding GC allocations.

### 9.3 Blur Background Throttling

The RenderTargetBitmap capture operation for blurred backgrounds is capped at 30fps and completely skipped when no frosted glass controls are visible. This optimization is further reduced in Balanced and Eco modes to ensure that the blur effect does not become a performance bottleneck.

### 9.4 Shared Noise Texture

All frosted glass controls and buttons share a single 128×128 noise texture instance. If 20 controls each independently generated their own noise texture, approximately 1.3MB of texture memory would be wasted. The sharing mechanism reduces this memory overhead to approximately 65KB.

### 9.5 Frame-Rate Normalization

Frame-rate normalization not only solves the problem of inconsistent animation speed across different refresh rate displays but also prevents unnecessary rendering on high-refresh-rate displays. On a 120Hz monitor, without normalization, animation speed would double, causing the user to perceive animations as overly rushed while also wasting GPU resources.

## 10. Security Enhancements

V1.4.27.0 builds upon the security mechanisms of V1.3.26.7, migrating some PowerShell-implemented security features into C# compiled code, improving the reliability and tamper resistance of security mechanisms.

### 10.1 C# IntegrityGuardService

In V1.3.x, integrity verification was implemented in PowerShell scripts, posing a theoretical risk of tampering—an attacker who could modify the PowerShell scripts could simultaneously modify the verification logic. V1.4.27.0 implements IntegrityGuardService in the pre-compiled C# DLL, with the verification logic compiled into IL code, significantly increasing the difficulty of tampering. This service automatically performs file integrity verification at application startup, validating whether the hash values of all core DLLs and script files match the expected values.

### 10.2 RSA Token Verification

The RSA token verification mechanism has been preserved and enhanced in V1.4.27.0. The token consists of four parts: nonce, timestamp, hashPayload, and signature. The verification process includes RSA signature verification, a time window check (60-second validity), and hash matching. The verification logic is implemented in C#, leveraging the .NET Framework's built-in RSACryptoServiceProvider to provide hardware-level key protection.

### 10.3 AES-256-CBC Elevation Token

Trust chain recovery in UAC elevation scenarios is implemented through AES-256-CBC encrypted elevation tokens. The token contains a nonce, timestamp, and payload, with the key derived via PBKDF2. The new process receives the token file path via the `-ElevationTokenPath` command-line argument, decrypts it, and verifies the script path and hash list contained in the payload. The token validity period is 120 seconds, slightly longer than the normal token window to accommodate the timing of UAC elevation operations.

### 10.4 Watchdog Monitoring Service

The WatchdogService monitors the application's running state, detecting abnormal exits, process hangs, and resource leaks. If an abnormal termination of the main process is detected, the WatchdogService triggers a secure cleanup process, clearing sensitive environment variables, temporary files, and session state. Communication between the watchdog and the main process is maintained through a heartbeat mechanism with a 5-second heartbeat interval and a 15-second timeout threshold.

### 10.5 Process Exit Secure Cleanup

V1.4.27.0 implements a three-tier exit cleanup mechanism. First tier: all Services implementing the IDisposable interface have their Dispose method called in sequence upon normal application exit. Second tier: handlers registered with the AppDomain.ProcessExit event forcefully clean up all resources upon process exit. Third tier: WeakReference tracks all resources that were not explicitly released, triggering final cleanup upon GC collection. This three-tier mechanism ensures that sensitive resources are properly cleaned up regardless of how the application exits.

V1.4.27.0 was designed with compatibility as a core constraint from the outset, ensuring that existing users and scripts can migrate seamlessly.

### 11.1 PowerShell 5.1 Compatibility

All C# code is compiled using the C# 5.0 language version, ensuring that the compiled DLLs can be loaded in the CLR 4.0 environment of PowerShell 5.1. C# 5.0 is the highest language version supported by PowerShell 5.1, and choosing this version ensures maximum compatibility.

### 11.2 Script Interface Compatibility

V1.4.27.0 maintains exactly the same PowerShell script interfaces as the V1.3.x series. All public function signatures, parameter names, parameter types, and return value types remain unchanged. ### 11.3 syncHash Synchronization Mechanism Compatibility

syncHash is the core synchronization mechanism used in V1.3.x for communication between PowerShell Runspaces and the UI thread. V1.4.27.0 maintains the syncHash data structure and communication protocol entirely unchanged, ensuring that existing communication code requires no modifications.

### 11.4 Command-Line Argument Compatibility

All command-line arguments remain consistent with the V1.3.x series, including `-GUI_Mode`, `-syncHash`, `-LanguageResource`, `-ElevationTokenPath`, `-LaunchedByExe`, and others. Users and external launchers do not need to modify any command-line arguments.

## 12. Known Limitations

As an architectural upgrade version, V1.4.27.0 has the following known limitations, which primarily stem from underlying constraints of the technology stack.

### 12.1 .NET Framework 4.8+

The full feature set of WPF requires .NET Framework 4.8 or later. V1.4.27.0 was developed and tested on .NET Framework 4.8, and compatibility issues may exist on earlier .NET Framework versions. Windows 10 and Windows 11 include .NET Framework 4.8 by default, but Windows 7 and Windows 8.1 require manual installation.

### 12.2 Windows 10+

WPF's DirectX rendering pipeline depends on the Windows Display Driver Model 2.0, which was first introduced in Windows 10. While Windows 7 and Windows 8.1 support WPF, certain rendering features such as high-performance blur effects may fall back to software rendering mode, resulting in performance degradation. The officially recommended runtime environment is Windows 10 version 1809 or later.

### 12.3 Approximation of GDI+-Specific Effects

Some GDI+-specific effects used in V1.3.x have no direct equivalent in WPF. For example, the complex multi-color gradient of PathGradientBrush is approximated in WPF through multiple overlaid RadialGradientBrush instances. This approximation is visually very close to the original, but subtle differences may exist in extreme cases, such as scenes with very large gradient color differences.
