## 1. Version Overview

V1.5.29.1 is an AURORA-Analyzer release focused on "depth visual expressiveness and switching robustness", building upon the V1.5.29.0 multi-level depth parallax reshape. This update centers on seven core areas:

1. **Quick-Switch Flashback Fix**: 6 IAuroraStaggerView views uniformly introduce the `_pendingEnterTimers` tracking list, canceling all pending entrance timers before the exit animation starts, eradicating the visual anomaly where "clicking the switch button before the animation finishes causes controls to flash back to their original position"
2. **Starfield Depth Visual Optimization**: Star Size coefficient 0.8→1.1 (~37% overall enlargement), CurrentRenderSize 0.55→0.7 (visible immediately on entrance), BaseAlpha upper limit 130→180 (higher bright-star ratio), making stars more prominent during depth motion
3. **Meteor-Style Halo Trail System**: During parallax, near-field stars (Depth>0.6) draw a LinearGradientBrush gradient halo trail. Trail length is driven by normalized velocity, direction adapts to zoomOut/zoomIn, EMA smoothing eliminates inter-frame jitter, and soft-threshold transition eliminates flicker
4. **View Depth Reallocation**: The depths of 5 dialog/detail views are reallocated, eliminating zero-span switches between peer views, so every click has visible depth feedback
5. **Admin Path Teleport Fix**: The admin path skips ElevationDialog, leaving the Splash→MainForm span at only 0.15 and causing starfield teleportation. A pre-parallax scheme is adopted — first dash to 0.30 in 500ms, then start NavigateTo, letting users clearly perceive starfield motion
6. **Mode-Switch Polling State Isolation Fix**: Fixes the issue where StartSyncHashPolling failed to reset the _pollingSuspended flag, causing the console to not echo and progress to be stuck at 50% after returning from Smart mode to the main window and then re-entering Pro mode; also fixes multiple connected issues including "content flashes then disappears" caused by async ClearConsole, cross-thread CollectionChanged not propagating in AppendConsoleLine, and DispatcherTimer being starved by Render
7. **Runspace Reuse Scope and Fast-Completing Engine Stability Fix**: Fixes the Assert-AuroraLaunchContext command-not-found error when running Pro Mode first then Smart Mode under Runspace reuse, the probabilistic 50% progress stuck issue when the smart engine completes quickly, and syncs the SecurityModule hash list after script modifications

For depth trails, V1.5.29.1 establishes a complete velocity-driven model:

## 2. Quick-Switch Flashback Fix (_pendingEnterTimers Pattern)

V1.5.29.1 fixes the issue where, during repeated switching between Pro mode, History mode, and Smart mode dedicated views, clicking an already-entered switch button before the animation finishes caused controls to suddenly flash back to their original position.

### 2.1 Background

The `DispatcherTimer` instances created by `PlayControlEnterAnimation` (per-tile stagger timers, fallback backup timers, listDelay list-item delay timers) are fire-and-forget. If the user clicks a switch button during the entrance animation to trigger `PlayStaggerExit`, these pending timers fire while the exit animation is in progress:

- **per-tile timers**: Call `BeginAnimation` to override the exit animation; the control jumps from mid-exit back to ScaleX=0, then re-enters to ScaleX=1 (flashback to original position)
- **fallback timers**: Directly force `tile.Opacity=1` + `ScaleX=1` + `Y=0`, overriding the exit animation
- **listDelay timers**: Trigger `PlayListItemEnterAnimation` to re-enter list items

### 2.2 Fix Pattern

Uniformly aligns with the ProModeView benchmark `_pendingEnterTimers` pattern:

1. Add a `_pendingEnterTimers` field to track all pending entrance timers
2. Add a `CancelPendingEnterTimers()` method to uniformly stop and clear timers
3. `PlayControlEnterAnimation` clears previous residuals at the start + registers each timer to the list
4. In the Timer Tick event, remove the fired timer from the list
5. `PlayControlExitAnimation` calls `CancelPendingEnterTimers()` at the start — the key fix

### 2.3 The 6 Fixed Views

| View | Tracked Timers | Status |
|------|----------------|--------|
| ProModeView | per-tile + fallback | ✅ Fixed |
| SmartModeView | per-tile + fallback | ✅ Fixed |
| ExportHistoryView | per-tile + fallback + listDelay | ✅ Fixed |
| SolutionDetailView | per-tile + fallback | ✅ Fixed |
| ElevationDialogView | per-tile + fallback | ✅ Fixed |
| SessionRestoreDialogView | per-tile + fallback | ✅ Fixed |

### 2.4 Unfixed Views (Evaluated as Not Needing Fix)

| View | Reason |
|------|--------|
| MainFormView | Mostly internal state switches; exit only staggers buttons + title; low override risk |
| SplashScreenView | One-time startup scenario; no quick-switch path |
| UndoViewerView | Exit uses `_closeSafetyTimer` as backup; no per-tile entrance timer chain |

### 2.5 Impact Scope

`ProModeView.xaml.cs`, `SmartModeView.xaml.cs`, `ExportHistoryView.xaml.cs`, `SolutionDetailView.xaml.cs`, `ElevationDialogView.xaml.cs`, `SessionRestoreDialogView.xaml.cs`.

## 4. Meteor-Style Halo Trail System

V1.5.29.1 introduces a meteor-style halo trail for starfield depth motion, reinforcing motion direction sense and visual feedback.

### 4.1 Trail Form Selection

V1.5.29.1 evaluated four trail forms and selected a hybrid "comet tail / halo elongation" scheme:

| Form | Visual Characteristic | Implementation | Performance Cost |
|------|----------------------|-----------------|------------------|
| Comet trail | Long tail follows, strong direction sense | LinearGradientBrush + DrawLine | Medium (new Brush per star) |
| Speed line | Short line points opposite to motion | Solid-color Pen + DrawLine | Low (zero-allocation possible) |
| Afterimage overlay | Multi-frame position overlay | Record N-frame history positions | High (N× rendering) |
| Halo elongation | Star body elongates along motion direction | DrawEllipse → rotated ellipse | Low |

The final choice is the LinearGradientBrush gradient halo trail (comet tail form), with the transparent end at tail and bright end at head, Pen width linked to star size.

### 4.2 Trigger Conditions

- Only during parallax (`isParallaxCycling && _parallaxVelocity > 0.0002`)
- Only near-field stars (Depth > 0.6, ~150-200 stars)
- Disappears immediately when parallax ends (not drawn in Idle state)

### 4.3 Velocity-Driven Model

Trail length is driven by **normalized velocity**, not displacement:

```
trailLen = (absoluteVelocity / parallaxSpan) × depth × 1500
```

After normalization, regardless of span size, the peak trail length is consistent. This solves the issue where small depth-difference scenes (e.g., MainForm→ProMode 0.15→0.50) had trails shortened by low absolute velocity.

### 4.4 Trail Direction Adaptation

A new `_parallaxDirection` field (+1=zoomOut / -1=zoomIn) is added, judged in `StartParallaxCycle` based on the difference between target phase and start phase:

- **zoomOut** (stars diffuse outward): trail end points to **center** (stars come from center)
- **zoomIn** (stars return inward): trail end points **outward** (stars come from outside)

### 4.5 EMA Smoothing and Soft-Threshold Transition

**EMA Exponential Moving Average** (α=0.3) eliminates trail length flicker caused by inter-frame jitter:

```
_parallaxVelocitySmooth = _parallaxVelocitySmooth × 0.7 + _parallaxVelocity × 0.3
```

**Soft-threshold transition** eliminates hard-threshold cutoff flicker:

| Normalized Velocity | Behavior |
|---------------------|----------|
| < 0.0002 | Not drawn |
| 0.0002 ~ 0.001 | trailIntensity linear 0→1 transition |
| > 0.001 | Full intensity drawing |

Both trail length and alpha are multiplied by `trailIntensity`, avoiding hard-cut flicker.

### 4.6 Trail Disappearance Semantics

The trail naturally shortens with velocity decay ("retracts"), and disappears immediately when parallax ends:

- Parallax acceleration phase: tail grows from nothing, gradually lengthens
- Parallax mid-phase (fastest): tail reaches peak length
- Parallax deceleration phase: tail naturally shortens
- Parallax end (stopped): tail fully disappears

In Idle state, `_parallaxVelocitySmooth *= 0.5` halves every frame, zeroing out within 2-3 frames with no residual flicker.

### 4.7 Trail Multiplier Tuning

The trail multiplier went through multiple rounds of tuning, dropping from 1200 to 600 to avoid the "rocket exhaust" feel:

| Version | Multiplier | Visual Effect |
|---------|------------|---------------|
| Initial | 1200 | Trail too long, like rocket exhaust |
| V1.5.29.1 | 600 | Trail moderate, naturally vivid |

### 4.8 Impact Scope

`AuroraStarfield.cs` StartParallaxCycle (_parallaxDirection/_parallaxSpan), OnRender (trail drawing), animation advance logic (_parallaxVelocitySmooth/EMA/soft-threshold).

## 6. Admin Path Teleport Fix (Pre-Parallax Scheme)

V1.5.29.1 fixes the starfield teleport issue where the admin path's Splash→MainForm skips ElevationDialog.

### 6.1 Background

The admin path (elevated process) skips ElevationDialog (depth 0.82), leaving the Splash(0.0)→MainForm(0.15) parallax span at only 0.15. After the starfield motion is occluded by the Splash exit and MainForm entrance animations, it visually looks like "suddenly jumping to a new position". The non-admin path Splash→ElevationDialog(0.82)→MainForm has a large span with sufficient motion, performing normally.

### 6.2 Fix Scheme

Adopts the **pre-parallax scheme**: before NavigateTo, first let the starfield run alone for 500ms, letting the user clearly see the starfield motion, then start Splash exit + MainForm entrance.

### 6.3 Timeline

| Time | Event | Starfield Phase |
|------|-------|-----------------|
| T=0 | Pre-parallax starts: 0.0→0.30 (500ms) | 0.0→0.30 |
| T=500 | Pre-parallax completes, NavigateTo starts | 0.30 |
| T=500 | Splash exit begins (800ms) + parallax 0.30→0.15 (2700ms) | 0.30→0.15 |
| T=1300 | Splash exit completes, Content switches to MainForm | ~0.21 |
| T=1300 | MainForm entrance (800ms) | ~0.21→0.17 |
| T=3200 | Parallax ends, settles at 0.15 | 0.15 |

### 6.4 Design Benefits

The user first sees 500ms of starfield motion (0.0→0.30), then Splash begins to exit and MainForm enters. The starfield motion is perceived by the user before Splash exits, eliminating the "stuck then jump" teleport feel.

### 6.5 Impact Scope

`SplashScreenView.xaml.cs` NavigateToMainForm.

## 7. Mode-Switch Polling State Isolation Fix

V1.5.29.1 fixes the issue where, after returning from Smart mode to the main window and then re-entering Pro mode, the console does not echo and progress is stuck at 50%.

### 7.1 Background

After completing analysis in Smart mode and returning to the main window, re-entering Pro mode and clicking "Start Analysis" results in the console not echoing at all and progress stuck at 50%. The user must click "Force Stop" before the console content floods in at once.

### 7.2 Root Cause

`ProModeViewModel.StartSyncHashPolling()` did not reset the `_pollingSuspended` flag to `false` when starting the syncHash polling timer. The flag was set to `true` in the following scenario and never cleared:

1. After SmartMode completes, `SuspendPolling()` sets `_pollingSuspended=true`
2. When returning to MainForm, `OnUnloaded` calls `SuspendPolling()` again (flag stays true)
3. When re-entering ProMode, `ResetForReentry()` takes the reset branch because `IsRunning=false` (correct, script has ended), but the flag stays true
4. User clicks "Start Analysis" → `StartAnalysisAsync` → `StartSyncHashPolling()` starts the timer
5. The timer callback executes, but `ProcessSyncHashSnapshot` detects `_pollingSuspended=true` and returns immediately
6. Logs/Progress/ScriptDone are all not processed → console does not echo, progress stuck at 50%
7. Clicking "Force Stop" → the finally block's `FlushRemainingLogOutput` bypasses `_pollingSuspended` and reads directly → content only then appears

### 7.3 Core Fix

`StartSyncHashPolling` resets `_pollingSuspended = false` at the beginning, ensuring the flag is clean each time polling starts.

### 7.4 Connected Fixes

While investigating the core root cause, several connected issues were also discovered and fixed:

| Issue | Root Cause | Fix |
|-------|------------|-----|
| Content flashes then disappears | `ClearConsole` uses async `BeginInvoke` to queue `ConsoleLines.Clear()`, and the subsequently synced `Add` content is overridden by the async clear | Changed to synchronous `Invoke`/direct call |
| Cross-thread CollectionChanged not propagating | `AppendConsoleLine` calling `ConsoleLines.Add` on a non-UI thread does not throw but the notification does not propagate to the UI | Uses `Dispatcher.CheckAccess()` to strictly determine the thread |
| DispatcherTimer starved by render | `_consoleFlushTimer` and `InvokeOnUiThread` use `BeginInvoke(Normal/Loaded)`, continuously delayed by AuroraStarfield's `CompositionTarget.Rendering` | `_syncHashTimer` callback changed to `Dispatcher.Invoke` (synchronous) |
| False screen clear when LogOutput is empty | `ProcessSyncHashSnapshot` calls `ClearConsole()` when LogOutput is empty or shortened; engine resetting LogOutput between phases causes the just-displayed logs to be cleared | Only resets `_lastLogLength`, does not clear the screen |

### 7.5 Impact Scope

`ProModeViewModel.cs` (StartSyncHashPolling/ProcessSyncHashSnapshot/ClearConsole/AppendConsoleLine/InvokeOnUiThread), `SmartModeViewModel.cs` (AppendConsoleLine/InvokeOnUiThread).

## 8. Runspace Reuse Scope and Fast-Completing Engine Stability Fix

V1.5.29.1 fixes two stability issues discovered after the polling state isolation fix: the Assert-AuroraLaunchContext command-not-found error when running Pro Mode first then terminating and running Smart Mode, and the probabilistic 50% progress stuck issue when the smart engine completes very quickly.

### 8.1 Background

Two user-reported symptoms occurred after the polling state isolation fix:

1. **Assert-AuroraLaunchContext Command Not Found**: Running Pro Mode first, then terminating it and running Smart Mode produces the error "The term 'Assert-AuroraLaunchContext' is not recognized as the name of a cmdlet, function, script file, or operable program."
2. **Probabilistic 50% Progress Stuck**: Entering Smart Mode directly does not error, but progress is probabilistically stuck at 50% or shows 100% — sometimes 100%, sometimes 50%.

### 8.2 Root Cause

1. **P7-1: SmartEngine lacks Get-Command guard; Runspace reuse causes function definition loss**: SmartEngine.ps1 calls Assert-AuroraLaunchContext directly without a Get-Command existence check (PRO-Engine.ps1 has this protection, SmartEngine lacks it). Under Runspace reuse, after ProMode terminates PRO Engine, the global variable $AURORA_LaunchGuard_Loaded=true persists. Although LaunchGuard.ps1 already removed the `return` to prevent skipping the function definition, Runspace state pollution can cause dot-source to execute incompletely, and the direct call triggers CommandNotFoundException.
2. **P7-2: Polling sampling timing issue when engine completes quickly; IsRunning already reset causes OnScriptComplete to not be called**: When SmartEngine completes very quickly (within 1 second), Progress changes rapidly from 50→80→100. The poll samples Progress=50, then SmartEngine instantly completes and sets ScriptDone=true. On the next poll, if IsRunning has already been reset to false by another path, OnScriptComplete is not called and Progress=100 is never set.
3. **P7-3: Hash list mismatch causes VerifyOrDie to force exit**: After modifying LaunchGuard.ps1 and SmartEngine.ps1, the hash list in SecurityModule.ps1 no longer matches. _integrityCacheDuration = TimeSpan.Zero (no cache), so CheckIntegrity re-verifies every time. A hash mismatch causes VerifyOrDie to return false, forcing SmartEngine to exit.

### 8.3 Core Fix

| Sub-item | Root Cause | Fix |
|----------|------------|-----|
| P7-1: Assert-AuroraLaunchContext Command Not Found | SmartEngine lacks Get-Command guard; Runspace reuse causes function definition loss | Align with PRO-Engine's defensive call pattern — check Get-Command for function existence before calling Assert-AuroraLaunchContext |
| P7-2: Progress Probabilistically Stuck at 50% | Polling sampling timing when engine completes quickly; IsRunning already reset causes OnScriptComplete not called | In SmartModeViewModel.cs ProcessSyncHashSnapshot, when ScriptDone=true is detected, force Progress=100 regardless of IsRunning state, then decide whether to call OnScriptComplete |
| P7-3: SecurityModule Hash List Sync | Hash list mismatch after script modifications causes VerifyOrDie to force exit | Update the SHA256 hashes of AURORA-LaunchGuard.ps1 and AURORA-SmartEngine.ps1 in AURORA-SecurityModule.ps1 |

### 8.4 Impact Scope

`Scripts\Engines\AURORA-SmartEngine.ps1` (LaunchGuard call site, lines 45-61), `AURORA.Wpf\ViewModels\SmartModeViewModel.cs` (ProcessSyncHashSnapshot, lines 690-707), `Scripts\Security\AURORA-SecurityModule.ps1` (hash list, lines 188 and 201).

## 10. Known Limitations

### 10.1 Trail GC Trade-off

The meteor-style halo trail uses LinearGradientBrush + GradientStop + Pen, newing objects per star per frame. During parallax, ~150 near-field stars × 60fps = 9,000 objects/s GC pressure. This violates the "zero-allocation hot path" hard constraint established in V1.5.28.5, but parallax is only 2.7s and already skips SoftGlow/DiffractionSpike/constellation-line rendering, so measured GC pressure is acceptable. If zero-allocation trails are needed in the future, the solid-color Pen speed-line scheme can be used (sacrificing gradient texture).

### 10.2 Trail Performance in Glass-Covered Areas

Glass blocks (AuroraFrostedGlassBorder) soften the trail — the trail behind a glass block becomes a blurry halo, and direction sense may be lost. This means the trail works best in non-glass areas (such as SmartModeView edges, ProModeView starfield-revealing areas), and is "eaten" in glass-covered areas. This is an inherent property of the glass material, not a defect.

### 10.3 Admin Path Starfield Final Phase

In the admin path pre-parallax scheme, the starfield finally settles at 0.15 (MainForm depth), but the pre-parallax first dashes to 0.30 then falls back. In rare cases, if the user performs a quick action during the 500ms pre-parallax, they may see the starfield in a mid-state near 0.30.

### 10.4 View Depth Reallocation Perception Difference

V1.5.29.1 reduces ProMode→History from 0.35 to 0.20, slightly reducing the shuttle feel. This is a necessary trade-off to spread out peer view depths (History/Undo/Permission/Session). History is a child dialog of ProMode, so the 0.20 span fits the "lightweight popup" semantics, but users accustomed to V1.5.29.0's strong shuttle feel may need to adapt.
