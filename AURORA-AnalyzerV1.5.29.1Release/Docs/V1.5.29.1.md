## 1. 版本概述

V1.5.29.1 是 AURORA-Analyzer 在 V1.5.29.0 多层深度视差重塑基础上的"纵深视觉表现力与切换稳健性"专项打磨版本。本次更新围绕六大核心领域展开：

1. **快速切换闪回修复**：6 个 IAuroraStaggerView 视图统一引入 `_pendingEnterTimers` 跟踪列表，在退场动画启动前统一取消所有待触发的入场定时器，根除"动效未结束前点击切换按钮导致控件闪现回原位"的视觉异常
2. **星场纵深视觉优化**：星点 Size 系数 0.8→1.1（整体放大约 37%）、CurrentRenderSize 0.55→0.7（入场即明显）、BaseAlpha 上限 130→180（亮星比例提升），让纵深运动期间星点更醒目
3. **流星式光晕拖尾系统**：视差期间为近景星（Depth>0.6）绘制 LinearGradientBrush 渐变光晕拖尾，拖尾长度由归一化速度驱动，方向适配 zoomOut/zoomIn，EMA 平滑消除帧间抖动，软阈值过渡消除闪烁
4. **视图深度重分配**：5 个对话框/详情视图的深度重新分配，消除同级视图零跨度切换，让每一次点击都有可见纵深反馈
5. **管理员路径瞬移修复**：管理员路径跳过 ElevationDialog 导致 Splash→MainForm 跨度仅 0.15 星场瞬移，采用前置视差方案——先 500ms 冲到 0.30 再启动 NavigateTo，让用户清晰感知星场运动
6. **模式切换轮询状态隔离修复**：修复 StartSyncHashPolling 漏重置 _pollingSuspended 标志导致从智能模式返回主窗口再进入专业模式后控制台不回显、进度卡 50% 的问题，同时修复 ClearConsole 异步清空导致的"内容闪一下后消失"、AppendConsoleLine 跨线程 CollectionChanged 不传播、DispatcherTimer 被 Render 饿死等多个连带问题
7. **Runspace 复用作用域与引擎快速完成稳定性修复**：修复先运行专业模式终止后再运行智能模式时 Assert-AuroraLaunchContext 命令未找到报错（SmartEngine 加 Get-Command 保护）、智能引擎快速完成时进度概率性卡 50%（强制推进 Progress=100）、SecurityModule 哈希清单同步三个子项

在纵深拖尾方面，V1.5.29.1 建立了完整的速度驱动模型：

| 维度 | V1.5.29.0 | V1.5.29.1 |

| 视差视觉反馈 | 极光层 +50% alpha | 极光层 +50% + 流星式光晕拖尾 |
| 拖尾驱动量 | 无拖尾 | 归一化速度 × depth × 倍率 |
| 拖尾方向 | 无 | zoomOut 指中心 / zoomIn 指外 |

## 2. 快速切换闪回修复（_pendingEnterTimers 模式）

V1.5.29.1 修复了在专业模式、历史模式和智能模式专属界面反复切换时，若在动效未结束前点击已入场的切换按钮导致控件突然闪现回原位的问题。

### 2.1 问题背景

`PlayControlEnterAnimation` 创建的 `DispatcherTimer`（per-tile 错峰定时器、fallback 兜底定时器、listDelay 列表项延迟定时器）是 fire-and-forget 的。若用户在入场动画期间点击切换按钮触发 `PlayStaggerExit`，这些待触发的定时器会在退场动画进行中触发：

- **per-tile 定时器**：调用 `BeginAnimation` 覆盖退场动画，控件从退场中途跳回 ScaleX=0 再重新入场到 ScaleX=1（闪现回原位）
- **fallback 定时器**：直接强制 `tile.Opacity=1` + `ScaleX=1` + `Y=0`，覆盖退场动画
- **listDelay 定时器**：触发 `PlayListItemEnterAnimation` 让列表项重新入场

### 2.2 修复模式

统一对齐 ProModeView 标杆的 `_pendingEnterTimers` 模式：

1. 添加 `_pendingEnterTimers` 字段跟踪所有待触发的入场定时器
2. 添加 `CancelPendingEnterTimers()` 方法统一停止并清除定时器
3. `PlayControlEnterAnimation` 开头清理上次残留 + 每个 timer 注册到列表
4. Timer 的 Tick 事件中从列表移除已触发定时器
5. `PlayControlExitAnimation` 开头调用 `CancelPendingEnterTimers()` 关键修复

### 2.3 修复覆盖的 6 个视图

| 视图 | 跟踪的定时器 | 状态 |
|------|-------------|------|
| ProModeView | per-tile + fallback | ✅ 已修复 |
| SmartModeView | per-tile + fallback | ✅ 已修复 |
| ExportHistoryView | per-tile + fallback + listDelay | ✅ 已修复 |
| SolutionDetailView | per-tile + fallback | ✅ 已修复 |
| ElevationDialogView | per-tile + fallback | ✅ 已修复 |
| SessionRestoreDialogView | per-tile + fallback | ✅ 已修复 |

### 2.4 未修复视图（评估后判定无需修复）

| 视图 | 原因 |
|------|------|
| MainFormView | 内部状态切换为主，退场仅按钮+标题错峰，覆盖风险低 |
| SplashScreenView | 一次性启动场景，无快速切换路径 |
| UndoViewerView | 退场用 `_closeSafetyTimer` 兜底，无 per-tile 入场定时器链 |

### 2.5 影响范围

`ProModeView.xaml.cs`、`SmartModeView.xaml.cs`、`ExportHistoryView.xaml.cs`、`SolutionDetailView.xaml.cs`、`ElevationDialogView.xaml.cs`、`SessionRestoreDialogView.xaml.cs`。

## 4. 流星式光晕拖尾系统

V1.5.29.1 为星场纵深运动引入流星式光晕拖尾，强化运动方向感与视觉反馈。

### 4.1 拖尾形态选择

V1.5.29.1 评估了四种拖尾形态后选择"彗星尾/光晕拉长"混合方案：

| 形态 | 视觉特征 | 实现方式 | 性能成本 |
|------|----------|----------|----------|
| 彗星拖尾 | 长尾巴跟随，强方向感 | LinearGradientBrush + DrawLine | 中（每星 new Brush） |
| 速度线 | 短线条指向运动反方向 | 单色 Pen + DrawLine | 低（可零分配） |
| 残影叠加 | 多帧位置叠加 | 记录 N 帧历史位置 | 高（N 倍绘制） |
| 光晕拉长 | 星点本体沿运动方向拉长 | DrawEllipse 改为旋转椭圆 | 低 |

最终选择 LinearGradientBrush 渐变光晕拖尾（彗星尾形态），透明端在 tail、亮端在 head，Pen 宽度与星点尺寸联动。

### 4.2 触发条件

- 仅视差期间（`isParallaxCycling && _parallaxVelocity > 0.0002`）
- 仅近景星（Depth > 0.6，约 150-200 颗）
- 视差结束立即消失（Idle 态不绘制）

### 4.3 速度驱动模型

拖尾长度由**归一化速度**驱动，而非位移：

```
trailLen = (absoluteVelocity / parallaxSpan) × depth × 1500
```

归一化后，无论跨度大小，拖尾峰值长度一致。解决了小深度差场景（如 MainForm→ProMode 0.15→0.50）拖尾被低绝对速度削短的问题。

### 4.4 拖尾方向适配

新增 `_parallaxDirection` 字段（+1=zoomOut / -1=zoomIn），在 `StartParallaxCycle` 中根据目标相位与起始相位的差值判断：

- **zoomOut**（星星向外扩散）：拖尾端指向**中心**（星星从中心来）
- **zoomIn**（星星向内归位）：拖尾端指向**外**（星星从外来）

### 4.5 EMA 平滑与软阈值过渡

**EMA 指数移动平均**（α=0.3）消除帧间隔抖动导致的拖尾长度闪动：

```
_parallaxVelocitySmooth = _parallaxVelocitySmooth × 0.7 + _parallaxVelocity × 0.3
```

**软阈值过渡**消除硬阈值切变闪烁：

| 归一化速度 | 行为 |
|------------|------|
| < 0.0002 | 不绘制 |
| 0.0002 ~ 0.001 | trailIntensity 线性 0→1 过渡 |
| > 0.001 | 满强度绘制 |

拖尾长度和 alpha 都乘以 `trailIntensity`，避免硬切闪烁。

### 4.6 拖尾消失语义

拖尾随速度衰减自然缩短（"缩进去"），视差结束立即消失：

- 视差启动加速段：尾巴从无到有，逐渐变长
- 视差中段最快：尾巴达到峰值长度
- 视差减速段：尾巴自然缩短
- 视差结束停住：尾巴完全消失

Idle 态 `_parallaxVelocitySmooth *= 0.5` 每帧减半，2-3 帧内归零，无残留闪烁。

### 4.7 拖尾倍率调优

拖尾倍率经过多轮调优，从 1200 降到 600，避免"火箭喷火"感：

| 版本 | 倍率 | 视觉效果 |
|------|------|----------|
| 初版 | 1200 | 拖尾过长，像火箭喷火 |
| V1.5.29.1 | 600 | 拖尾适中，自然灵动 |

### 4.8 影响范围

`AuroraStarfield.cs` StartParallaxCycle（_parallaxDirection/_parallaxSpan）、OnRender（拖尾绘制）、动画推进逻辑（_parallaxVelocitySmooth/EMA/软阈值）。

## 6. 管理员路径瞬移修复（前置视差方案）

V1.5.29.1 修复了管理员路径 Splash→MainForm 跳过 ElevationDialog 导致星场瞬移的问题。

### 6.1 问题背景

管理员路径（已提权进程）跳过 ElevationDialog（深度 0.82），导致 Splash(0.0)→MainForm(0.15) 视差跨度仅 0.15。星场运动量被 Splash 退场和 MainForm 入场动画遮挡后，视觉上像"突然跳到新位置"。非管理员路径 Splash→ElevationDialog(0.82)→MainForm 跨度大，运动量充足，表现正常。

### 6.2 修复方案

采用**前置视差方案**：在 NavigateTo 之前先让星场单独跑 500ms，让用户清晰看到星场运动，然后再启动 Splash 退场 + MainForm 入场。

### 6.3 时序

| 时间 | 事件 | 星场相位 |
|------|------|----------|
| T=0 | 前置视差启动：0.0→0.30（500ms） | 0.0→0.30 |
| T=500 | 前置视差完成，启动 NavigateTo | 0.30 |
| T=500 | Splash 退场开始（800ms）+ 视差 0.30→0.15（2700ms） | 0.30→0.15 |
| T=1300 | Splash 退场完成，Content 切换到 MainForm | ~0.21 |
| T=1300 | MainForm 入场（800ms） | ~0.21→0.17 |
| T=3200 | 视差结束，停在 0.15 | 0.15 |

### 6.4 设计收益

用户会先看到 500ms 的星场运动（0.0→0.30），然后 Splash 才开始退场，MainForm 入场。星场运动在 Splash 退场前就被用户感知到，不再有"卡一下然后跳"的瞬移感。

### 6.5 影响范围

`SplashScreenView.xaml.cs` NavigateToMainForm。

## 7. 模式切换轮询状态隔离修复

V1.5.29.1 修复了从智能模式返回主窗口后再进入专业模式时，控制台不回显、进度卡 50% 的问题。

### 7.1 问题背景

从智能模式完成分析后返回主窗口，再进入专业模式点击"开始分析"，控制台完全不回显，进度卡在 50%。用户必须点击"强行停止"后，控制台内容才一次性涌入。

### 7.2 根因

`ProModeViewModel.StartSyncHashPolling()` 方法在启动 syncHash 轮询定时器时，没有重置 `_pollingSuspended` 标志为 `false`。该标志在以下场景下被设为 `true` 且未被清除：

1. SmartMode 完成后调用 `SuspendPolling()` 设 `_pollingSuspended=true`
2. 返回 MainForm 时 `OnUnloaded` 再次调用 `SuspendPolling()`（标志保持 true）
3. 重入 ProMode 时 `ResetForReentry()` 因 `IsRunning=false` 走重置分支，不恢复轮询（正确，脚本已结束），但标志保持 true
4. 用户点"开始分析" → `StartAnalysisAsync` → `StartSyncHashPolling()` 启动定时器
5. 定时器回调执行，但 `ProcessSyncHashSnapshot` 检测到 `_pollingSuspended=true` 直接 return
6. 日志/进度/ScriptDone 全部不被处理 → 控制台不回显、进度卡 50%
7. 点"强行停止" → finally 块的 `FlushRemainingLogOutput` 绕过 `_pollingSuspended` 直接读取 → 内容才显示

### 7.3 核心修复

`StartSyncHashPolling` 开头重置 `_pollingSuspended = false`，确保每次启动轮询时标志是干净的。

### 7.4 连带修复

在排查核心根因过程中，还发现并修复了多个连带问题：

| 问题 | 根因 | 修复 |
|------|------|------|
| 内容闪一下后消失 | `ClearConsole` 用异步 `BeginInvoke` 排队 `ConsoleLines.Clear()`，后续同步 `Add` 的内容被异步清空覆盖 | 改为同步 `Invoke`/直接调用 |
| 跨线程 CollectionChanged 不传播 | `AppendConsoleLine` 在非 UI 线程调用 `ConsoleLines.Add` 不抛异常但通知不传播到 UI | 用 `Dispatcher.CheckAccess()` 严格判断线程 |
| DispatcherTimer 被渲染饿死 | `_consoleFlushTimer` 和 `InvokeOnUiThread` 用 `BeginInvoke(Normal/Loaded)`，被 AuroraStarfield 的 `CompositionTarget.Rendering` 持续占用推迟 | `_syncHashTimer` 回调改用 `Dispatcher.Invoke`（同步） |
| LogOutput 为空时误清屏 | `ProcessSyncHashSnapshot` 中 LogOutput 为空或变短时调用 `ClearConsole()`，引擎 Phase 间重置 LogOutput 导致刚显示的日志被清空 | 只重置 `_lastLogLength`，不清屏 |

### 7.5 影响范围

`ProModeViewModel.cs`（StartSyncHashPolling/ProcessSyncHashSnapshot/ClearConsole/AppendConsoleLine/InvokeOnUiThread）、`SmartModeViewModel.cs`（AppendConsoleLine/InvokeOnUiThread）。

## 8. Runspace 复用作用域与引擎快速完成稳定性修复

本章描述 V1.5.29.1 在 P6 修复之后追加的 P7 级别稳定性修复，解决先运行专业模式终止后再运行智能模式时出现的 Assert-AuroraLaunchContext 命令未找到报错，以及智能引擎快速完成时进度概率性卡 50% 的问题。

### 8.1 问题背景

用户反馈两个稳定性问题：

1. **Assert-AuroraLaunchContext 报错**：先运行专业模式并终止后再运行智能模式，智能引擎启动时出现"无法将"Assert-AuroraLaunchContext"项识别为 cmdlet、函数、脚本文件或可运行程序的名称"错误，智能模式无法启动。
2. **进度概率性卡 50%**：直接进入智能模式不报错，但进度卡在 50% 和 100% 之间是看概率的——有时候能到 100%，有时候卡在 50% 不动。

### 8.2 根因

三个独立根因叠加：

1. **P7-1 SmartEngine 缺少 Get-Command 保护**：`AURORA-SmartEngine.ps1` 直接调用 `Assert-AuroraLaunchContext`，没有像 `PRO-Engine.ps1` 那样用 `Get-Command` 检查函数是否存在再调用。Runspace 复用场景下，ProMode 终止 PRO Engine 后全局变量 `$AURORA_LaunchGuard_Loaded=true` 残留，虽然 `LaunchGuard.ps1` 已移除 return 防止跳过函数定义，但 Runspace 状态污染可能导致 dot-source 不完整执行，直接调用触发 CommandNotFoundException。
2. **P7-2 引擎快速完成时轮询采样时序问题**：SmartEngine 执行很快时（1 秒内完成），Progress 从 50→80→100 快速变化。轮询采样到 Progress=50 后 SmartEngine 瞬间完成设置 `ScriptDone=true`，但下次轮询检测到 `ScriptDone=true` 时若 `IsRunning` 已被其他路径重置为 false，`OnScriptComplete` 不会被调用，Progress=100 未设置。
3. **P7-3 哈希清单不匹配导致 VerifyOrDie 强制退出**：修改 `LaunchGuard.ps1` 和 `SmartEngine.ps1` 后，`SecurityModule.ps1` 中的哈希清单不匹配。`_integrityCacheDuration = TimeSpan.Zero`（无缓存），每次 CheckIntegrity 都重新校验，哈希不匹配会导致 VerifyOrDie 返回 false，SmartEngine 强制退出。

### 8.3 核心修复

| 子项 | 修复方式 |
|------|----------|
| P7-1 Assert-AuroraLaunchContext 报错 | 对齐 PRO-Engine 的防御性调用，先 `Get-Command` 检查函数是否存在再调用 |
| P7-2 进度概率性卡 50% | `ProcessSyncHashSnapshot` 检测到 `ScriptDone=true` 时，无论 `IsRunning` 状态如何，都强制设置 `Progress=100`，然后再判断是否调用 `OnScriptComplete` |
| P7-3 哈希清单同步 | 更新 `AURORA-SecurityModule.ps1` 中 `AURORA-LaunchGuard.ps1` 和 `AURORA-SmartEngine.ps1` 的 SHA256 哈希 |

### 8.4 影响范围

- `Scripts\Engines\AURORA-SmartEngine.ps1`（第 45-61 行，LaunchGuard 调用保护）
- `AURORA.Wpf\ViewModels\SmartModeViewModel.cs`（第 690-707 行，ProcessSyncHashSnapshot）
- `Scripts\Security\AURORA-SecurityModule.ps1`（第 188 行和第 201 行，哈希清单）

## 10. 已知限制

### 10.1 拖尾的 GC 权衡

流星式光晕拖尾使用 LinearGradientBrush + GradientStop + Pen，每星每帧 new 对象。视差期间约 150 颗近景星 × 60fps = 9,000 对象/秒 GC 压力。这违反 V1.5.28.5 建立的"零分配热路径"硬约束，但视差仅 2.7 秒且已跳过 SoftGlow/DiffractionSpike/星座连线等昂贵渲染，实测 GC 压力可接受。若未来需要零分配拖尾，可改用单色 Pen 速度线方案（牺牲渐变质感）。

### 10.2 拖尾在玻璃块覆盖区的表现

玻璃块（AuroraFrostedGlassBorder）会柔化拖尾——拖尾在玻璃块后面会变成一团模糊光晕，方向感可能丢失。这意味着拖尾在非玻璃区域（如 SmartModeView 的边缘、ProModeView 的星场透出区）效果最好，在玻璃块覆盖区效果会被吃掉。这是玻璃材质的固有特性，非缺陷。

### 10.3 管理员路径星场最终相位

管理员路径前置视差方案中，星场最终停在 0.15（MainForm 深度），但前置视差先冲到 0.30 再回落。极少数情况下若用户在 500ms 前置视差期间快速操作，可能看到星场在 0.30 附近的中途状态。

### 10.4 视图深度重分配的感知差异

V1.5.29.1 将 ProMode→历史从 0.35 降到 0.20，穿梭感略减。这是为了让同级视图（历史/撤销/权限/会话）拉开深度的必要权衡。历史作为 ProMode 的子级对话框，0.20 跨度符合"轻量弹窗"语义，但用户若习惯 V1.5.29.0 的强穿梭感可能需要适应。
