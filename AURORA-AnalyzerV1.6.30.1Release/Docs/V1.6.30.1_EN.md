## 1. Version Overview

V1.6.30.1 is an AURORA-Analyzer release focused on "execution flow robustness and rollback closure completeness", building upon the solution view execution window optimization. This update covers three core areas: comprehensive refactor of the solution view execution window, complete audit fixes (6 P0 + 12 P1 + 3 audit-newly-discovered low-severity defects), and GlassDialogAnimation unified encapsulation. MSBuild compiles with zero errors and zero warnings.

For execution window refactor, V1.6.30.1 upgrades the solution view execution interface to a step-timeline + log dual-pane layout, introduces the `Process.Kill` whole-process-tree cancellation mechanism, the `FailureAction.Abort/Continue/AskUser` three-state failure handling, progress interpolation and remaining-time estimation based on the average duration of executed commands, and `EvaluatePreCheck` pre-validation filtering for solutions with no executable commands.

For rollback closure completeness, V1.6.30.1 fixes critical defects including non-retryable undo failures, orphaned disk snapshots from expired sessions accumulating, missing terminal-state protection, and dirty states left by Continue mode not executing rollback commands — ensuring the undo chain is closed end-to-end from trigger to cleanup.

V1.6.30.1 achieves a comprehensive upgrade through the following core strategies:

3. **P1 Defect Fixes (12 Items)**: terminal-state protection, disk snapshot cleanup, orphaned snapshot loading, success-semantics contradiction, Continue rollback, snapshot trigger conditions, registry path extraction, cancellation token propagation, event unsubscription, GlassDialogAnimation unified encapsulation
4. **Composite Cross-Audit Fixes (3 Items)**: empty-solution semantics, terminal-state BackupSnapshotId override, UI not refreshing after Undo
5. **GlassDialogAnimation Unified Encapsulation**: three public methods + `onSafetyTimerCreated` callback overload + centralized animation-duration constants

## 2. Chapter 1: Solution View Execution Window Comprehensive Refactor

V1.6.30.1 comprehensively refactors the execution window of the SolutionDetailView, upgrading from a single-pane log to a step-timeline + log dual-pane layout, and introducing four core mechanisms: process-tree cancellation, three-state failure handling, progress estimation, and pre-validation filtering.

### 2.1 Step Timeline + Log Dual-Pane Layout

The execution window is upgraded to a dual-pane layout with a step timeline on the left and real-time log on the right. The left timeline displays the `FixPhase` state-machine status of each step in execution order (pending/executing/success/failed/skipped), while the right side scrolls the command output log in real time.

- **Left timeline**: Users can intuitively perceive which step is currently executing, which phase the overall progress is in, which steps have succeeded, and which have been skipped — without digging through logs
- **Right log echo**: Retains the original real-time log output capability, kept in sync with the timeline state

The dual-pane layout separates "macro progress" from "micro logs", preventing heavy output from burying key step information in a single-pane log.

### 2.2 Cancel and Terminate Child Processes

On execution cancellation, `Process.Kill` is called to terminate the entire process tree rather than only the parent process, avoiding orphaned process residuals.

- **Background**: The original cancel logic only sent a termination signal to the top-level PowerShell process; child processes (such as nested script invocations and external commands) were not terminated together, causing handle leaks and long-term orphaned process occupation
- **Fix**: On cancellation, traverse and `Kill` the entire process tree to ensure all derived processes exit synchronously

### 2.3 Failure Continue/Abort Choice

Introduces the `FailureAction.Abort/Continue/AskUser` three-state failure handling strategy:

| FailureAction | Behavior |
|---------------|----------|
| Abort | Immediately aborts the entire session after a command failure; no subsequent commands are executed |
| Continue | First executes the failing command's `RollbackCommand`, then skips this step and continues with subsequent commands |
| AskUser | Pops up a dialog asking the user to decide Abort or Continue |

Key design of Continue mode: **execute the rollback command before skipping**, ensuring a single-step failure does not leave a dirty state affecting subsequent commands (see Chapter 3, P1-6 for details).

### 2.4 Progress Interpolation + Time Estimation

Estimates remaining time based on the average duration of executed commands:

```
avgMs = sum(executedCommandDuration) / executedCount
remainingMs = avgMs × remainingCount
```

- The progress bar advances by linear interpolation of "executed command count / total command count"
- Remaining time is dynamically computed from the average duration of executed commands and continuously refined as execution proceeds
- Users get intuitive "how much longer" feedback during execution

### 2.5 Pre-Validation for No Executable Commands

`EvaluatePreCheck` filters solutions with no executable commands before formal execution:

- **Background**: The original logic returned `Success` directly for empty solutions (all commands filtered out by PreCheck), which is semantically incorrect — doing nothing should not be a success
- **Fix**: If no executable commands remain after PreCheck, return `PartialSuccess` instead of `Success`, making the status semantics more accurate

### 2.6 Impact Scope

`SolutionDetailView.xaml` (dual-pane layout), `SolutionDetailView.xaml.cs` (execution flow, cancellation, progress estimation), related ViewModels (`FixPhase` state machine, `FailureAction` three-state, `EvaluatePreCheck`).

## 3. Chapter 2: P0 Defect Fixes (6 Items)

V1.6.30.1 completes 6 P0 defect fixes, covering high-severity issues such as deadlocks, non-retryable operations, resource leaks, missing Dispose, exit without fallback, and uncleared timers.

### 3.1 P0-1: OnFixCommandFailure Unloaded Deadlock

**Issue**: `OnFixCommandFailure` still attempted UI operations after the view was Unloaded, deadlocking with the cancellation token callback.

**Fix**: Use `token.Register` to register a cancellation callback that completes the `TaskCompletionSource` via `TrySetResult`; catch `ObjectDisposedException` to prevent the callback from throwing when the token is already disposed, which would cause a deadlock.

### 3.2 P0-2: Undo Failure Non-Retryable

**Issue**: After an undo operation failed, the session's `CanUndo` was set to `false`, preventing the user from retrying the undo — but the disk snapshot still existed, forming a "snapshot exists but undo not allowed" deadlock.

**Fix**:

- Keep `CanUndo=true` after undo failure to allow retry
- Expiry cleanup logic links to `RemoveBackupSnapshot` to reclaim disk snapshots of expired sessions
- Clean up orphaned snapshots on startup (residuals from abnormal exits in previous runs)

### 3.3 P0-3: Retry Does Not Clean Up Old CTS Leak

**Issue**: On retry, a new `CancellationTokenSource` was created directly without calling `Cancel` + `Dispose` on the old instance, causing CTS resource leaks and cancellation-signal confusion.

**Fix**: Before creating a new CTS, `Cancel` then `Dispose` the old instance, ensuring the cancellation signal propagates correctly and unmanaged resources are released.

### 3.4 P0-4: 6 Views' _exitHandle Not Disposed in OnUnloaded

**Issue**: The `_exitHandle` (exit animation handle / event handle) of the following 6 views was not disposed in `OnUnloaded`, causing handle leaks:

| View | Status |
|------|--------|
| ProModeView | ✅ Fixed |
| SmartModeView | ✅ Fixed |
| SplashScreenView | ✅ Fixed |
| ExportHistoryView | ✅ Fixed |
| SolutionDetailView | ✅ Fixed |
| SessionRestoreDialogView | ✅ Fixed |

**Fix**: Uniformly call `Dispose` on `_exitHandle` in `OnUnloaded`.

### 3.5 P0-5: MainFormView.PlayStaggerExit Without Fallback

**Issue**: `MainFormView.PlayStaggerExit` lacked a fallback logic; if staggered exit scheduling failed, the exit animation would hang and the view could not complete the switch.

**Fix**: Use `StaggerExitHelper.ScheduleExit` for unified scheduling, with a built-in fallback timer ensuring the exit completes within a safe time limit even if staggered scheduling is abnormal.

### 3.6 P0-6: SolutionDetailView._pendingEnterTimers Not Cleared in OnUnloaded

**Issue**: `SolutionDetailView`'s `_pendingEnterTimers` was not cleared via `CancelPendingEnterTimers` in `OnUnloaded`, so pending entrance timers kept executing in the background after the view was unloaded, causing cross-view state corruption (same root cause as the V1.5.29.1 flashback fix).

**Fix**: Call `CancelPendingEnterTimers()` in `OnUnloaded` to uniformly cancel and clear all pending entrance timers.

### 3.7 Impact Scope

`SolutionDetailView.xaml.cs`, `ProModeView.xaml.cs`, `SmartModeView.xaml.cs`, `SplashScreenView.xaml.cs`, `ExportHistoryView.xaml.cs`, `SessionRestoreDialogView.xaml.cs`, `MainFormView.xaml.cs`, related ViewModels (undo/retry/CTS management).

## 4. Chapter 3: P1 Defect Fixes (12 Items)

V1.6.30.1 completes 12 P1 defect fixes, covering medium-severity issues such as terminal-state protection, snapshot reconciliation, success semantics, rollback commands, registry paths, cancellation tokens, event subscriptions, and animation unification.

### 4.1 P1-1: CompleteRepairSession Terminal-State Protection

**Issue**: `CompleteRepairSession` still overwrote `Status` and `CanUndo` when the session was already in a terminal state (Success/Failed/Aborted), rolling back the terminal state.

**Fix**: If already in a terminal state, return directly without overwriting `Status` / `CanUndo`, preserving terminal-state immutability.

### 4.2 P1-2: Memory Eviction Does Not Clean Up Disk Snapshots

**Issue**: When a session was evicted due to memory pressure, only in-memory objects were cleaned up; the corresponding disk snapshots were not cleaned up together, causing disk orphaned snapshots to accumulate.

**Fix**: Expiry cleanup logic links to `RemoveBackupSnapshot`; memory eviction synchronously deletes disk snapshots.

### 4.3 P1-3: UndoViewer Does Not Load Disk Snapshots

**Issue**: `UndoViewer` only displayed in-memory snapshots and did not load disk snapshots, so after a restart users could not see orphaned snapshots from the previous run and could not clean them up manually.

**Fix**: `LoadAllSnapshots` loads disk snapshots; orphaned snapshots are displayed as placeholder items that users can clean up manually.

### 4.4 P1-5: overallSuccess Contradicts PartialSuccess

**Issue**: The `overallSuccess` determination contradicted the `PartialSuccess` status — when some commands succeeded and some were skipped, `overallSuccess` was still true, but the status was marked `PartialSuccess`.

**Fix**: Tighten the `overallSuccess` determination to:

```
overallSuccess = executedCount > 0
             && successCount == executedCount
             && skippedCount == 0
```

That is: commands were executed, all succeeded, and none were skipped — only then is it considered a complete success.

### 4.5 P1-6: Continue Mode Does Not Execute RollbackCommand

**Issue**: In Continue mode, after a command failure the step was skipped directly to continue with subsequent commands, without first executing the current command's `RollbackCommand`, leaving dirty states that affected subsequent commands.

**Fix**: In Continue mode, execute the step's `RollbackCommand` before skipping, then continue with subsequent commands.

### 4.6 P1-7: Snapshot Trigger Conditions Do Not Match Comments

**Issue**: The trigger conditions for disk snapshots did not match the code comments — the comments claimed "only registry/service commands trigger snapshots", but the actual logic coverage was inconsistent.

**Fix**: Align comments and implementation to ensure snapshots are triggered when covering registry/service commands.

### 4.7 P1-8: Registry Path Extraction Too Simplistic

**Issue**: Registry path extraction only supported `HKLM`/`HKCU`, not `HKCR`/`HKU`/`HKCC`, and the extraction logic was simplistic (a single regex match).

**Fix**: Support all root keys `HKCR`/`HKU`/`HKCC`, and use loop extraction to handle commands containing multiple registry paths.

### 4.8 P1-9: EvaluatePreCheck Passes CancellationToken.None

**Issue**: `EvaluatePreCheck` was called with `CancellationToken.None`, so user cancellation could not interrupt the PreCheck phase.

**Fix**: Pass the actual `CancellationToken` to ensure the cancellation signal propagates in the PreCheck phase as well.

### 4.9 P1-10: ProModeView Events Not Unsubscribed

**Issue**: `ProModeView`'s `ConsoleLines.CollectionChanged` event was not unsubscribed in `OnUnloaded`, and `SuspendPolling` was not called correctly, so the view still received console updates after being unloaded.

**Fix**: Unsubscribe `ConsoleLines.CollectionChanged` in `OnUnloaded` and call `SuspendPolling` correctly.

### 4.10 P1-11: SmartModeView Events Not Unsubscribed + SuspendPolling

**Issue**: `SmartModeView` had the same root issue as `ProModeView` — events not unsubscribed and `SuspendPolling` not called.

**Fix**: Align with the `ProModeView` fix pattern: unsubscribe events and call `SuspendPolling`.

### 4.11 P1-12/B4: GlassDialogAnimation Zero Calls

**Issue**: The `GlassDialogAnimation` utility class existed but had zero calls; 10 glass dialogs still used inline animation implementations, with 11+ duplicate code sites.

**Fix**: Migrate the 10 inline animations to the `GlassDialogAnimation` unified encapsulation (see Chapter 5 for details).

### 4.12 Impact Scope

`SolutionDetailViewModel.cs` (terminal-state protection / success semantics / Continue rollback / snapshot trigger / registry path / PreCheck token), `UndoViewerViewModel.cs` (disk snapshot loading), `ProModeView.xaml.cs` (event unsubscribe / SuspendPolling), `SmartModeView.xaml.cs` (event unsubscribe / SuspendPolling), `GlassDialogAnimation.cs` (unified encapsulation), various glass dialog views (migration call sites).

## 5. Chapter 4: Composite Cross-Audit Newly Discovered Fixes (3 Items)

Building on the P0/P1 fixes, V1.6.30.1 discovered and fixed 3 low-severity defects through composite cross-audit, covering three intersecting areas: empty-solution semantics, terminal-state field override, and UI refresh.

### 5.1 Audit A-1: Empty-Solution Status / Success Semantics Contradiction

**Issue**: For empty solutions (executedCount==0), the `isPartial` determination was insufficient, causing empty solutions to be misjudged as PartialSuccess rather than a clear "no executable command" status.

**Fix**: Add the `executedCount == 0` condition to the `isPartial` determination, making the empty-solution status semantics clearer — neither a complete success nor a partial success, but a special "no executable command" state.

### 5.2 Audit B-1: Terminal-State Protection Branch Still Updates BackupSnapshotId

**Issue**: The terminal-state protection branch of `CompleteRepairSession`, although not overwriting `Status`/`CanUndo`, still updated `BackupSnapshotId`, tampering with the snapshot reference of terminal-state sessions.

**Fix**: Remove the assignment to `BackupSnapshotId` in the terminal-state protection branch; only update `FinishedAt`, preserving the immutability of the snapshot reference for terminal-state sessions.

### 5.3 Audit E-2: UI Does Not Refresh After Undo Success

**Issue**: After an undo operation completed successfully, properties such as `CanUndo` were already updated, but the UI did not fire `PropertyChanged` notifications, so button states, snapshot lists, and other interface elements were not refreshed in time.

**Fix**: After Undo success, manually fire `PropertyChanged` notifications for the relevant properties to ensure the UI stays in sync with the ViewModel state.

### 5.4 Impact Scope

`SolutionDetailViewModel.cs` (isPartial determination / terminal-state BackupSnapshotId removal / PropertyChanged after Undo), related ViewModel base classes (notification mechanism).

## 7. Chapter 6: History Analysis and Report Export Experience Upgrade

V1.6.30.1 upgrades the history view analysis entry and the report export dialog, covering six improvements: a unified Analyze button with dynamic icon feedback, a multi-select sync refresh fix, a cross-archive trend data source fix, a report format mutual exclusion fix, a report export bilingual adaptation, and format option card hover feedback.

### 7.1 Unified Analysis Button with Dynamic Icon Feedback

**Change**: Merged the "Trend" and "Timeline" bottom buttons in the history view into a single "Analyze" button, reducing button count. The button text and icon dynamically switch based on the selected archive count:

| Selected Count | Button Text | Icon | Behavior |
|----------------|-------------|------|----------|
| 0 | Analyze | Magnifier | Disabled |
| 1 | Timeline | Clock | Single-archive internal event distribution |
| ≥2 | Trend | Rising line chart | Cross-archive health evolution |

The `AuroraButton` control is extended with `IconGeometry`/`IconSize`/`IconTextGap` dependency properties for icon+text combined rendering. The hot path is zero-allocation via `Geometry.Freeze` + cached `Brush`/`Pen`. The extension is backward compatible — `IconGeometry` defaults to `null`, leaving other buttons unaffected.

**Reason**: Two separate buttons (Trend/Timeline) cluttered the bottom bar and required users to know in advance which analysis suited their selection. A single context-aware button reduces cognitive load and adapts automatically.

**Impact Scope**: `AuroraButton.cs`, `ExportHistoryViewModel.cs`, `ExportHistoryView.xaml`.

---

### 7.2 Multi-Select Sync Refresh Fix

**Issue**: `SuspendSelectedEntriesNotifications` suspended `CollectionChanged` during batch sync of `SelectedEntries`, causing `OnSelectedEntriesChanged` to never fire and leaving button text/icons stale after a batch selection operation.

**Fix**: Added a `NotifySelectionBatchCompleted()` public method to the ViewModel, called by the View after `ResumeSelectedEntriesNotifications()`, to refresh button text/icons/batch-delete text.

**Impact**: The Analyze button text (Timeline/Trend), the Analyze button icon (clock/line chart), and the batch-delete button text all update correctly after batch selection changes.

**Impact Scope**: `ExportHistoryViewModel.cs`, `ExportHistoryView.xaml.cs`.

---

### 7.3 Cross-Archive Trend Data Source Fix

**Issue**: `BuildTrendData` iterated `_entries` (all archives) instead of `_selectedEntries` (selected archives), causing the trend chart to show full history instead of the selected data subset.

**Fix**: Changed the data source from `_entries` to `_selectedEntries`.

**Impact**: The trend chart now correctly reflects only the selected archives, making cross-archive comparison meaningful.

**Impact Scope**: `ExportHistoryViewModel.cs`.

---

### 7.4 Report Format Mutual Exclusion Fix

**Issue**: Three `RadioButton`s in `ReportFormatDialogView` belonged to different `Grid` parent containers. WPF's default mutual-exclusion scope is the same parent, causing exclusion failure — all three radio buttons could be lit up simultaneously.

**Fix**: Added `GroupName="ReportFormatGroup"` to all three `RadioButton`s for cross-container mutual exclusion. Additionally, the `SelectedFormat` setter was supplemented to raise `PropertyChanged` for the corresponding `Is*Selected` properties.

**Impact Scope**: `ReportFormatDialogView.xaml`, `ReportFormatDialogViewModel.cs`.

---

### 7.5 Report Export Bilingual Adaptation

**Issue**: `ReportFormatDialogViewModel` depended on the global `LanguageService.IsChinese`, while `ExportHistoryViewModel` uses its own `_language` field. This caused language desynchronization — the main interface could be in English while the report format dialog displayed Chinese.

**Fix**: The `ReportFormatDialogViewModel` constructor now accepts an `isChinese` parameter. `IsChinese`/`LanguageName` properties were added to the ViewModel. All `LanguageService.IsChinese`/`CurrentLanguageName` references in the View were replaced with ViewModel properties. `ExportHistoryView` passes `_viewModel.IsChinese` when constructing the dialog.

This establishes a unified language chain: `ExportHistoryViewModel._language` → `ReportFormatDialogViewModel._isChinese` → `ReportGeneratorService` → `HtmlReportExporter`/`XlsxReportExporter`.

**Impact Scope**: `ReportFormatDialogViewModel.cs`, `ReportFormatDialogView.xaml.cs`, `ExportHistoryView.xaml.cs`.

### 7.6 Format Option Card Mouse Hover Feedback

**Issue**: The three format option cards in `ReportFormatDialogView` had no hover feedback, and `HighlightSelectedOption` created a new `SolidColorBrush` each time, causing abrupt visual transitions and per-allocation GC pressure.

**Fix**: Changed card `Background`/`BorderBrush` to named `SolidColorBrush` instances, and used `ColorAnimation` (200ms) for hover fade-in/fade-out plus a smooth selection-state transition. A four-state color design is applied:

| State | Background | Border |
|-------|------------|--------|
| Unselected base | #221E2D40 | #551E2D40 |
| Unselected hover | #331E2D40 | #881E2D40 |
| Selected base | #334DA0E8 | #FF4DA0E8 |
| Selected hover | #4450A8E8 | #FF4DA0E8 |

This aligns with the `ExportHistoryView` list-item hover feedback and eliminates per-alloc brush GC pressure by reusing brush instances and animating only the `Color` property.

**Impact Scope**: `ReportFormatDialogView.xaml`, `ReportFormatDialogView.xaml.cs`.

## 9. Known Limitations

### 9.1 ViewModel Command Event Subscriptions Under NavigationCache Reuse Mode

Under `NavigationCache` reuse mode, ViewModel command events retain their subscriptions — this is a design tradeoff of NavigationCache, avoiding the overhead of re-subscribing on every view switch. `OnLoaded` re-subscribes to `ConsoleLines` to ensure console echo works correctly. This is a design tradeoff, not a defect.

### 9.2 safetyTimer Management for GlassDialogAnimation PlayGlassExit

The `safetyTimer` of `GlassDialogAnimation.PlayGlassExit` must be managed by the caller via the `onSafetyTimerCreated` callback. This callback is only needed for the `ProModeView` ModalOverlay reuse scenario — in that scenario, the safetyTimer is held externally by `ProModeView` and managed under unified cancellation. Other migration sites do not use the callback overload; the safetyTimer is managed internally by `GlassDialogAnimation`.
