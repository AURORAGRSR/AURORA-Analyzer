## 1. Version Overview

V1.5.28.0 is a comprehensive reshaping release for the AURORA-Analyzer view system and animation language. This update centers on five core areas:

1. **Completely Unified Aurora Animation Design**: Unifying all views' window-level and control-level animations to a single parameter contract, covering enter, exit, switch, staggered enter, and modal enter/exit across the full lifecycle
2. **New Unified View Layout Design**: Establishing a unified layout vocabulary of borderless transparent window shell + AuroraStarfield starfield background + AuroraFrostedGlassBorder glass container + 3:2 left-right split + Aurora self-drawn scrollbar

5. **New Solution View**: SolutionDetailView providing metric comparison table, solution list, rule details, and one-click fix execution entry

In terms of animation unification, V1.5.28.0 converges the previously inconsistent enter/exit/switch parameters across views into a unified contract:

| Animation Layer | Unified Parameters |
|-----------------|---------------------|
| Window Enter | Scale 1.15→1.0, 600ms AuroraCustomBackEase EaseOut + Opacity 0→1, 600ms CubicEase EaseOut |

In terms of view layout, V1.5.28.0 establishes a unified layout vocabulary for the three new views — SmartModeView, ExportHistoryView, and SolutionDetailView: borderless transparent window, AuroraStarfield starfield background layer, Grid Margin=24 content area, 3:2 left-right split, AuroraFrostedGlassBorder glass container, AuroraFrostedGlassCard rounded modal, Aurora self-drawn scrollbar.

This update is a "comprehensive view system reshaping, completely unified animation language, bottom-layer interface compatible" release. ## 2. Completely Unified Aurora Animation Design

V1.5.28.0 unifies all views' animations to a single parameter contract, covering three levels: window-level, control-level, and modal-level.

### 2.1 Window-Level Enter Animation

All windows (SplashScreenView, MainFormView, ProModeView, SmartModeView, ExportHistoryView, SolutionDetailView, ElevationDialogView, SessionRestoreDialogView, PerformanceUpgradeDialogView, PermissionInfoView) unify their enter animation to:

- **ScaleTransform**: 1.15 → 1.0, 600ms, AuroraCustomBackEase (EaseOut)
- **Opacity**: 0 → 1, 600ms, CubicEase (EaseOut)
- **RenderTransformOrigin**: Window-level `0.5,0.5`, TransformGroup containing ScaleTransform + TranslateTransform
- **XAML Preset**: ScaleTransform preset to `ScaleX="1.15" ScaleY="1.15"` to avoid first-frame flicker
- **Starfield Lock**: `StarfieldBg.IsWindowAnimating = true` during enter, unlock on completion

AuroraCustomBackEase implements the original PowerShell formula `f(t) = 1 - (1-t)³·(1+3t)` via `EaseInCore` returning `t³·(4-3t)` with `EasingMode.EaseOut`. This implementation deliberately avoids WPF's built-in BackEase having a 0 value at t=0 (which would leave the scale channel static on the first frame).

PlayMainWindowEnter appends a V1.5 liquid glass micro-rebound after the 600ms enter: 1.0→1.03 (120ms QuadraticEase EaseOut) →1.03→1.0 (280ms QuarticEase EaseOut), triggered via a 600ms-delayed DispatcherTimer.

### 2.2 Window-Level Exit Animation

All windows' exit is unified to a three-phase "wind-up — scale-up leave — fade-out":

| Phase | Scale | Duration | Easing | Opacity |
|-------|-------|----------|--------|---------|
| Wind-up | 1.0 → 0.97 | 80ms | QuadraticEase EaseOut | — |
| Scale-up Leave | 0.97 → 1.15 | 720ms | QuadraticEase EaseOut | — |
| Fade | — | 800ms | CubicEase EaseOut | 1 → 0 |

Exit flow: set `IsHitTestVisible = false` to prevent repeated triggers → `StarfieldBg.IsWindowAnimating = true` to lock starfield → launch wind-up + scale-up + fade parallel animations → execute cleanup callback on completion (StopAnimation + Close + Shutdown). The exit uses "scale-up departure" rather than "scale-down departure" — the window flies toward the observer and dissipates like a star, echoing the starfield theme.

### 2.3 Control-Level Staggered Enter Animation

All views' control staggered enter is unified to 80ms stagger + 450ms main animation + 525ms jelly convergence:

- **Stagger Delay**: Adjacent tile delay 80ms (`staggerMs = 80`), triggered sequentially via DispatcherTimer
- **Main Animation**: Scale 0 → 1.07, 450ms, CubicEase EaseOut; Opacity 0 → 1, 450ms CubicEase EaseOut; Y offset 100 → 0
- **Jelly Convergence**: After main animation reaches 1.07, 1.07 → 1.0, 525ms, QuarticEase EaseOut
- **Glass Block Special Handling**: Glass material tile's Scale start point changed from 0 to 1.0 (avoiding per-frame blur texture recalculation jitter), still targeting 1.07 as overshoot

This parameter contract is uniformly implemented in SmartModeView.PlayControlEnterAnimation, ExportHistoryView.PlayControlEnterAnimation, and SolutionDetailView.PlayControlEnterAnimation. AnimationHelper.PlayMetroStaggerEnter serves as a reusable helper (defaults staggerMs=30, durationMs=320, offsetY=60, Windows 8.1 Metro original values); views override these to the unified 80/450/100 standard when calling.

### 2.4 Modal Dialog Animation

Modal overlays (ModalOverlay, UserInputOverlay, MessageOverlay) enter/exit animations are unified to a three-channel UWP animation:

**Enter**:
- Overlay Opacity 0 → 1
- Content Scale 0.92 → 1.07 → 1.0 (three-phase: 0.92→1.07 main animation 360ms CubicEase EaseOut, 1.07→1.0 jelly convergence 525ms QuarticEase EaseOut)
- Content Y 24 → 0

**Exit**:
- Content Scale 1.0 → 0.97 wind-up (80ms QuadraticEase) → 0.97 → 1.15 leave (720ms QuadraticEase)
- Content Y 0 → -16
- Overlay Opacity 1 → 0, 800ms CubicEase EaseOut

This contract is uniformly implemented in SmartModeView.AnimateModalOverlay, ExportHistoryView.ShowGlassMessage/ShowGlassConfirm, and SolutionDetailView's modal methods.

### 2.5 1500ms Fallback Timer

All views' control staggered enter is equipped with a 1500ms fallback timer. On trigger, it force-stops all tile animations and resets `Opacity = 1`, `ScaleX/ScaleY = 1.0`, `Translate X/Y = 0`, ensuring controls remain visible even if Dispatcher timers fail to fire due to thread congestion or window Hide/Show.

This mechanism is the direct fix for the ConsoleBox background magnification defect — when the enter animation's ScaleTransform gets stuck at an intermediate value (e.g., 0 or 1.07), BlurLayer's CroppedBitmap crop area becomes too small, causing a magnification effect after stretching. The 1500ms fallback timer force-resets the transform state, eliminating this problem at its root.

### 2.6 View Switch Animation

View switches between ProModeView and SmartModeView, ExportHistoryView and SolutionDetailView use dedicated switch animations (distinct from cold-start enter):

**Switch Out (PlaySwitchOutAnimation)**:
- Scale 1.0 → 0.97 wind-up (80ms QuadraticEase EaseOut) → 0.97 → 1.15 leave (720ms QuadraticEase EaseOut)
- Opacity 1 → 0, 800ms CubicEase EaseOut
- Completion callback constructs and shows the target window

**Switch In (PlaySwitchInAnimation)**:
- Scale start point reset to 1.1 (distinct from cold-start's 1.15, a lighter re-entry curve)
- Scale 1.1 → 1.0, 600ms CubicEase EaseOut
- Opacity 0 → 1, 500ms CubicEase EaseOut
- Re-register `AuroraMaterialPipeline.Current.SetBackgroundSource(StarfieldBg)` to restore glass material background source
- Resume polling `_viewModel.ResumePolling()`

## 3. New Unified View Layout Design

V1.5.28.0 establishes a unified layout vocabulary for all views, covering window shell, background layer, content container, split ratio, scrollbar, and modal layer.

### 3.1 Borderless Transparent Window Shell

All views share a borderless transparent window shell:

- `WindowStyle="None"`, `AllowsTransparency="True"`, `Background="Transparent"`
- `ResizeMode="NoResize"`, `Topmost="False"`, `RenderTransformOrigin="0.5,0.5"`
- Pre-installed `TransformGroup` (ScaleTransform + TranslateTransform)
- Most views start with `Opacity="0"`, driven by the enter animation for fade-in

Window size conventions: MainForm 400×480, SplashScreen 420×190, Elevation/ProMode 750×750, PermissionInfo 520×520, SmartMode/ExportHistory/SolutionDetail 1000×700.

### 3.2 AuroraStarfield Starfield Background Layer

AuroraStarfield is the universal background layer for all views, and the registered background source for AuroraMaterialPipeline (`SetBackgroundSource(StarfieldBg)`). It exposes the `IsWindowAnimating` property, switching to degraded rendering mode during window enter/exit/switch animations (reducing star count and draw frequency, skipping breathing effects and meteor effects) to lower GPU load.

Optional properties include `StatusText`, `StatusTextX/Y`, `StatusTextAlignment`, `StarCount`.

### 3.3 AuroraFrostedGlassBorder Glass Container

AuroraFrostedGlassBorder is the universal content container, used in two ways:

- **Raw**: `CornerRadius=8`, `BorderThickness=0`, for content sections (console area, menu area, list area, detail area)
- **AuroraFrostedGlassCard Style**: `CornerRadius=12`, for modal dialogs and popups, providing stronger glass quality and rounded corners

It renders 4 glass effect layers (background layer + top highlight stroke + inner scattering layer), consistent with AuroraConsoleBox's color scheme.

### 3.4 3:2 Left-Right Split Layout

The main content areas of SmartModeView, ExportHistoryView, and SolutionDetailView uniformly adopt a 3:2 left-right split:

- Column definitions: `3*/12/2*` (left column 3 parts, 12px spacer, right column 2 parts)
- Left column: main operation area (console / history list / comparison table)
- Right column: auxiliary information area (executable repair items / history details / solution details)

Content cards use semi-transparent `#11000000` background, CornerRadius=6, Padding 12-14.

### 3.5 Aurora Self-Drawn Scrollbar

The unified AuroraScrollBarStyle + AuroraScrollViewerStyle is replicated across SmartModeView, ExportHistoryView, SolutionDetailView, and ProModeView (ProModeView is the canonical version):

- Width 10-14px, CornerRadius=5
- Track `#19141E32`, border `#2D6496DC` 0.5px
- Thumb gradient `#64B0D2FF` → `#5096C8FF`
- Hover `#82B4E1FF` / `#94C4E5FF`
- Drag `#AAC8F0FF` / `#B8D4F5FF`
- Thumb template includes 40%-height top highlight `#40FFFFFF` → `#00FFFFFF` and drag radial glow `#28C8E6FF`

### 3.6 Modal Overlay Unification

All major views share the modal overlay pattern:

- Root-level `Grid x:Name="...Overlay" Background="#800A1428" Visibility="Collapsed"`
- Contains `AuroraFrostedGlassBorder` with `AuroraFrostedGlassCard` style (CornerRadius=10-12, Padding=24-28, MinWidth=360-400, MaxWidth=520-580, centered)
- Inner structure uniformly a 3-row grid: title (16pt bold accent color) + scrollable body (12pt, LineHeight=20) + centered confirm/cancel AuroraButton row (140×40, 6px margins)

### 3.7 Title Bar and Bottom Action Bar

- **Title Bar**: 3-column `Auto/*/Auto` grid, left return/action button, center AuroraTextBlock title (`AnimatedText` binding), right action buttons horizontal StackPanel
- **Bottom Action Bar**: Right-aligned StackPanel or multi-column Grid, uniformly 32-40px height AuroraButtons, 8-12px right margins

## 7. View Switching and Window Handoff Mechanism

V1.5.28.0 adopts an independent window handoff mechanism replacing in-place visibility toggles, covering two view-switch pairs: ProMode↔SmartMode and ExportHistory↔SolutionDetail.

### 7.1 Independent Window ViewModel Handoff

Mode switching uses a "hide host + show owned window + restore on close" pattern:

- Host view plays switch-out animation then Hide
- Construct owned window, set Owner = host
- Owned window takes over syncHash interaction (avoiding dual-ViewModel conflict)
- Owned window closes → host restores: Show + switch-in animation + re-register AuroraMaterialPipeline background source + resume polling

### 7.2 ProModeView ↔ SmartModeView Switch

- ProModeViewModel triggers ShowSmartModeRequested (replacing former IsSmartMenuVisible flag)
- ProModeView.OnShowSmartModeRequested plays PlaySwitchOutAnimation; completion callback constructs SmartModeView and Show
- SmartModeView.OnWindowLoaded calls StartPolling, plays enter animation
- On return, SmartModeView.PlayWindowExitAnimation exits and Close
- ProModeView.OnSmartModeClosed plays PlaySwitchInAnimation, re-registers background source, resumes polling

### 7.3 ExportHistoryView ↔ SolutionDetailView Switch

- ExportHistoryView.OpenSolutionDetail plays exit animation (Scale 1.0→1.15 + Opacity 1→0, 500ms CubicEase) then Hide
- Constructs SolutionDetailView, ShowDialog
- After SolutionDetailView closes, ExportHistoryView restores (Show + Scale 1.15→1.0 + Opacity 0→1, 500ms)

### 7.4 Background Source Re-registration

On switch-in animation completion, calls `AuroraMaterialPipeline.Current.SetBackgroundSource(StarfieldBg)` to re-register the glass material background source. This is because the background source may become invalid during window Hide; re-registration ensures the glass material can correctly sample the starfield background.

## 8. Defect Fixes

### 8.1 ConsoleBox Background Magnification Issue

**Issue**: AURORACONSOLE exhibited visual anomalies in the background after shrinking — the background appeared magnified several times. Root cause was ConsoleBox enter animation's ScaleTransform residual — the animation used two DispatcherTimers to implement a 0→1.07→1.0 scale effect, but when timers failed to fire due to Dispatcher congestion or window Hide/Show, the ScaleTransform got stuck at an intermediate value (e.g., 0 or 1.07). The original fallback timer only reset Opacity without resetting scale, causing BlurLayer's CroppedBitmap crop area to be too small, producing a magnification effect after stretching.

**Fix**: In ProModeView.xaml.cs's fallback timer, in addition to resetting Opacity=1, added force reset of ScaleTransform.ScaleX/ScaleY=1.0 and TranslateTransform.Y=0. This fix was subsequently upgraded to the unified 1500ms fallback timer mechanism across all views.

### 8.2 SmartMode Key Name Mismatch Causing Echo Failure

**Issue**: SmartModeViewModel's syncHash key names did not match SmartEngine's actual key names, causing authorization signal failure, SmartEngine blocking on WaitOne(30000) with a 30-second timeout, and dialogs displaying blank due to Hashtable parsing errors.

**Fix**: Corrected key names in ProcessSyncHashSnapshot (e.g., `SmartAnalysisAuthRequired` → `SmartAnalysisRequested`, `RequiresDecision` → `RequiresAuthorization`, removed `MenuWaiting`), added `RequiresElevation` detection and `InputType=="UseExportedLogs"` branch. Fixed CloseModal authorization signals (e.g., `SmartAnalysisAuthorized=true` + `SmartAnalysisRequested=false` + SignalAuthorizationEvent()). Fixed dialog display (ShowDecisionModal's PendingCommand parsing, ShowResultModal's resultObj.ToString() correctly parsing ActionName/Result/Output/ExecutionTime, added ShowElevationModal and ShowExportedLogsModal).

### 8.3 PROENGINE Falsely Triggering SmartEngine

**Issue**: After running PROENGINE and returning to the main window, running a previously executed SMARTENGINE incorrectly launched the Smart Mode view. Root cause was residual syncHash.SmartMenuItems data in the PowerShell session.

**Fix**: Added cleanup logic in ProModeViewModel's StartAnalysisAsync method — clearing SmartMenuItems, ExecutedMenuIndices, resetting signatures, and setting IsSmartMenuVisible=false at the start of each new analysis session, ensuring a clean state and preventing false triggers from old data.

## 10. Known Limitations

### 10.1 Lightweight Re-entry for View Switching

PlaySwitchInAnimation uses a 1.1 starting scale (rather than cold-start's 1.15) and CubicEase easing (rather than AuroraCustomBackEase) — this is a deliberate lighter re-entry curve, distinct from cold-start window enter. Users may notice that re-entry is slightly faster than first launch when frequently switching views.

### 10.2 Glass Block Animation Start Point

In control staggered enter, glass material tile's Scale start point is changed from 0 to 1.0 (avoiding per-frame blur texture recalculation jitter), so glass blocks' enter visual effect differs slightly from non-glass tiles — glass blocks do not have a scale-up-from-0 process, but rather overshoot from 1.0 to 1.07 then converge.

### 10.3 Independent Window Resource Overhead

SmartModeView, ExportHistoryView, and SolutionDetailView, as independent windows, each maintain their own AuroraStarfield starfield background instance and AuroraMaterialPipeline background source. On low-spec devices, frequent view switching may introduce brief starfield background rebuild overhead.
