## 1. 版本概述

V1.5.28.5 是 AURORA-Analyzer 在 V1.5.28.0 视图重塑基础上的渲染机制重构与控制台模式易用性升级版本。本次更新围绕七大核心领域展开：

1. **渲染机制重构与刷新率自适应**：引入启动时探测、动态分级、渲染层级订阅、后端回退链、频率自适应和远程会话检测六位一体的 GPU 利用优化机制，并根据屏幕实际刷新率对动效帧率进行归一化独立适配，显著提升图形界面的流畅跟手程度
2. **控制台模式 GUI/CLI 双模式兼容**：打造 AURORA-SmartEngine-CLI.ps1 适配层，让 SmartEngine 在纯控制台环境下也能完成提权、授权、CSV 导出确认、提权补救与主菜单循环五个 GUI 等待点的交互

4. **PRO 模式控件入场动效修复**：将固定 1500ms 兜底定时器升级为动态计算公式，根除尾部控件入场动画被强制跳变的问题
5. **历史视图与解决方案视图多项优化**：修复命中检测机制、新增解决方案入口、优化底部按钮错峰入场动效、优化撤销管理器
6. **主窗口与全局视觉细节优化**：调整语言列表顺序、优化启动画面文字布局、UWP 状态文本同步、模态对话框遮罩动效与视觉效果
7. **大量安全更新**：修补提权命令行参数注入、Invoke-Expression 命令注入与缓存投毒、完整性校验 TOCTOU 窗口等关键漏洞

## 2. 渲染机制重构与刷新率自适应

V1.5.28.5 对图形渲染管线进行了全面重构，建立六位一体的 GPU 利用优化机制，并根据屏幕实际刷新率对动效帧率进行归一化独立适配。

### 2.1 启动时探测

App.xaml.cs 在应用启动时执行三阶段探测：

- **渲染模式选择**：`RenderOptions.ProcessRenderMode = RenderMode.Default`，让 WPF 自动决定（优先硬件，软件回退）。刻意不使用 `HardwareOnly`，因为无 GPU 驱动的机器上会抛异常
- **初始分级**：`int initialTier = RenderCapability.Tier >> 16`（0=软件渲染、1=2D 硬件、2=高级硬件），同时订阅 `RenderCapability.TierChanged` 监听运行时分级变化
- **硬件能力探测**：调用 `AuroraRenderEngine.DetectPerformanceTierAndReturn()` 和 `MaterialCapabilities.Current`，获取 cores、gpuName、gpuVendor、d3d9ex、gpuVramMB、gpuScore、recommendedBackend 完整诊断信息

MaterialCapabilities.Probe 通过 P/Invoke 探测 d3dcompiler_47.dll（LoadLibrary）和 Direct3DCreate9Ex（D3D9Ex 设备支持），并执行远程会话双路检测。

### 2.2 动态分级

根据探测结果，AURORA-Analyzer 划分为四个性能挡位：

| 挡位 | 触发条件 | 模糊捕获频率 | 星空重绘 |
|------|----------|--------------|----------|
| Eco | RenderCapability.Tier == 0 或远程会话 | 100ms（10fps） | 降级 |
| Balanced | 低端 GPU 或显存不足 | 66ms（15fps） | 标准 |
| Performance | 主流 GPU | 50ms（20fps） | 标准 |
| Extreme | 高端 GPU | 33ms（30fps） | 全特效 |

### 2.3 渲染层级订阅

AuroraMaterialPipeline 采用惰性订阅模式：

- 首个 AuroraMaterialComposer 注册时自动订阅 `CompositionTarget.Rendering`
- 最后一个 Composer 注销时退订，防止空转消耗
- `_isRenderingSubscribed` 标志确保订阅状态一致性

该机制确保当所有玻璃材质组件不可见时，渲染回调完全停止，避免无意义的每帧计算。

### 2.4 后端回退链

模糊后端采用三级回退链（SelectBlurBackend）：

1. **Tier == 0（软件渲染）→ RtbBlurBackend（强制）**：软件渲染下 ShaderEffect HLSL PS 3.0 在 CPU 上运行，比 RTB+BlurEffect 更慢
2. **Tier >= 1 → ShaderEffectBackend（如果可用）**：HLSL PS 3.0 GPU 9 抽头高斯模糊，依赖 d3dcompiler_47.dll 和 AuroraBlurShaderEffect 编译成功；不可用时回退
3. **最终回退 → RtbBlurBackend**：Win7+ 默认始终可用

`ReloadBlurBackend()` 在 GPU 驱动崩溃、电源模式切换或远程会话连接/断开时触发，销毁旧后端、重新选择、重置背景采样缓存强制下一帧重新捕获。

### 2.5 频率自适应

`GetBackgroundCaptureThrottleMs()` 根据当前挡位动态返回节流值：

```
Tier == 0（软件渲染） → 100ms（10fps）
PerformanceTier.Eco   → 66ms（15fps）
PerformanceTier.Balanced → 50ms（20fps）
Performance / Extreme  → 33ms（30fps）
```

该值被 `CaptureBackgroundIfNeeded` 用于节流背景采样捕获，避免每帧执行昂贵的 `RTB.Render`。

### 2.6 远程会话检测

MaterialCapabilities.DetectRemoteSession 采用双路检测：

- **快速路径**：`GetSystemMetrics(SM_REMOTESESSION = 0x1000)` via user32.dll P/Invoke
- **精确路径**：`ProcessIdToSessionId` → `WTSQuerySessionInformation(WTSConnectState)` → 读取 4 字节整型状态。仅 `WTSActive=0` 视为真正的本地会话，其余状态（WTSConnected=1、WTSDisconnected=4、WTSDown=7 等）均视为远程
- **失败保守**：检测失败时保守地假设为非远程（避免误禁用 GPU 后端）

检测到远程会话时：强制禁用 DWM 后端（RDP 无法渲染 Acrylic）、`SupportsShaderEffect = false`、强制回退 RTB 软件模糊。

### 2.7 动效帧率归一化（45fps 基准）

V1.5.28.5 修正了动效归一化基准。原代码将 timeScale 分母设为 16.667（60fps 理论值），但 DispatcherTimer 在 Render 优先级下受 Dispatcher 队列调度抖动影响，实际平均帧率约为 45fps。基准与实际不匹配导致动效视觉速度比设计预期快约 33%。

修复将三个动效控件的 timeScale 分母从 16.667 改为 22.222：

| 控件 | 文件 | 修改位置 |
|------|------|----------|
| AuroraButton | AuroraButton.cs:725 | 悬停/颜色/辉光/焦点/按压/弹簧/加载/环境/磁吸 |
| AuroraTaskHUD | AuroraTaskHUD.cs:257 | 呼吸/图标/过渡 |
| AuroraProgressBar | AuroraProgressBar.cs:202 | 进度平滑/辉光位置/粒子年龄 |

归一化后各刷新率对应的 timeScale：60Hz → 0.75、120Hz → 0.375、160Hz → 0.281、320Hz → 0.141。Eco 模式下使用 1.0 timeScale + 33ms 节流，不进行归一化。

## 3. 控制台模式 GUI/CLI 双模式兼容

V1.5.28.5 全新打造了 AURORA-SmartEngine-CLI.ps1 适配层，让 SmartEngine 在纯控制台环境下也能完成完整的智能修复流程。

### 3.1 三层架构

AURORA-SmartEngine-CLI.ps1 采用三层设计：

1. **预创建线程安全 syncHash**：`$global:syncHash = [hashtable]::Synchronized(@{})`，LogOutput 使用 `[System.Collections.ArrayList]::Synchronized(...)`，确保跨 Runspace 可见
2. **后台 Runspace 执行 SmartEngine.ps1**：保留原始逻辑不做任何修改，通过 `$ps.BeginInvoke()` 异步启动
3. **主线程轮询 syncHash**：主线程循环轮询，使用 `Read-Host` 响应所有 GUI 事件

### 3.2 五个 GUI 等待点

SmartEngine.ps1 在执行流程中有五个阻塞等待用户输入的点，CLI 适配层逐一接管：

| # | SmartEngine 等待点 | syncHash 键 | CLI 响应方式 |
|---|--------------------|-------------|--------------|
| 1 | 预提权等待（299-309 行） | RequiresElevation / ElevationAuthorized | Read-Host + 启动管理员进程 |
| 2 | 授权 EventWaitHandle 等待（425 行） | AuthorizationEventName + Authorized | Read-Host + Set 事件 |
| 3 | CSV 导出日志确认（1187-1194 行） | RequiresUserInput / UserInput | Read-Host 选择 y/n |
| 4 | catch 分支提权补救（687-697 行） | 同 #1 | 同 #1 |
| 5 | 主菜单事件循环（1618-1720 行） | IsHostAlive / UserInput / Authorized / PendingCommand | Read-Host 菜单选择 |

### 3.3 轮询状态机

CLI 适配层的主循环包含完整的轮询状态机：

- **4.3 提权请求处理**：检测 `RequiresElevation == $true`，提示用户，设置 `ElevationAuthorized = $true/false`，重置 `RequiresElevation = $false`，睡眠 5 秒等待 SmartEngine 调用 `Invoke-SafeExit`
- **4.4 授权请求处理**：检测 `RequiresAuthorization -eq $true -and $null -eq $Authorized`，显示 `PendingCommand`，'s' 键设置 `Authorized = $false`
- **4.5 CSV 导出确认**：检测 `RequiresUserInput -eq $true`，提示"[y] 使用已导出的日志 [n] 重新扫描"
- **4.7 菜单输入处理**：'m' 输入直接在 CLI 侧重印菜单，不触发 SmartEngine 交互

### 3.4 启动安全

CLI 适配层在启动时执行 RSA 令牌验证 + 父进程验证。仅 `-FromPRO` / `-GUI_Mode` 开关不被信任（任何用户都可添加），必须验证 `syncHash` 已存在于全局作用域中才允许执行。

### 3.5 接入点

AURORA-SmartEngine-CLI.ps1 集成到 AURORA-AnalyzerPRO.ps1 的 `-ConsoleMode` 分支，性能升级对话框和 MainForm View 2 控制台按钮均可访问该 CLI 适配层。

### 3.6 编码与修复

CLI 适配层添加 UTF-8 BOM 解决中文 Windows 上的编码错误，调整 AddScript 调用，重新格式化 elseif 语句，修改字符串转义。修复了执行结果不打印（过早状态检测 + Read-Host 线程阻塞）、提权取消后需手动 'm' 刷新（状态变更遗漏）、菜单重复打印（冗余日志 + 'm' 命令未处理）等问题。

## 5. PRO 模式控件入场动效时间跳变修复

### 5.1 问题

ProModeView.PlayControlEnterAnimation 的 16 个控件中，尾部控件（ExitButton 延迟 1120ms、MinimizeButton 延迟 1200ms）的主动画（450ms）尚未完成时，固定 1500ms 兜底定时器就触发并强制重置 ScaleTransform 到终态，导致动画"突然加速"的视觉跳变。

### 5.2 根因

固定 1500ms 兜底定时器是为 V1.5.28.0 的较少控件数量设计的。当 ProModeView 控件增加到 16 个后，最后一个控件的动画完成时间为 (16-1)×80 + 450 + 525 = 2175ms，远超 1500ms。

### 5.3 修复

将兜底定时器改为动态计算公式：

```
fallbackMs = (tiles.Count - 1) * staggerMs + durationMs + bounceDurationMs + 100
```

对于 ProModeView 的 16 个控件：(16-1) × 80 + 450 + 525 + 100 = **2275ms**，确保所有控件动画完成后再触发兜底。

### 5.4 参数

| 参数 | 值 | 说明 |
|------|----|------|
| staggerMs | 80 | 相邻 tile 交错延迟 |
| durationMs | 450 | 主动画时长（0→1.07 Scale + 0→1 Opacity + 100→0 Y） |
| bounceDurationMs | 525 | 果冻收敛时长（1.07→1.0） |
| 缓冲 | 100ms | Dispatcher 调度抖动容差 |

### 5.5 影响范围

ProModeView.xaml.cs PlayControlEnterAnimation 的兜底定时器计算逻辑。

## 6. 历史视图命中检测机制修复

### 6.1 健康分计算修复（整数除法截断）

**问题**：ExportHistoryService.ComputeHealthScore 使用整数除法 `totalIssues * 100 / totalEvents`，当 totalIssues 较小（如 1 个 warning）且 totalEvents 较大（如 200）时，整数除法截断导致扣分为 0，健康分错误地返回 100。

**修复**：提取为公共静态方法，使用浮点运算：

```csharp
public static int ComputeHealthScore(int critical, int error, int warning, int totalEvents)
{
    if (totalEvents <= 0) return 100;
    int totalIssues = critical * 3 + error * 2 + warning;
    double score = 100.0 - (double)totalIssues * 100.0 / (double)totalEvents;
    return Math.Max(0, (int)Math.Round(score));
}
```

权重：critical=3、error=2、warning=1。HistoryMatchService 调用同一方法确保公式一致。

### 6.2 扫描窗口动态扩展

**问题**：HistoryMatchService 使用固定 24h 扫描窗口，当导出日志的时间范围超过 24h 时，刚导出的日志因超出窗口而匹配失败。

**修复**：新增 ComputeScanWindowHours 方法动态计算窗口：

- 默认 24h
- 取 max(24h, DateRange 起始日期到现在的跨度)
- 上限 720h（30 天）

支持单日期（yyyyMMdd）和日期范围（start-end）两种格式。DateRange 跨度超过 24h 时自动扩展窗口，确保覆盖导出时间范围。

### 6.3 影响范围

ExportHistoryService.cs ComputeHealthScore、HistoryMatchService.cs ComputeScanWindowHours 及 Detect 调用链。

## 11. 安全更新批量加固

V1.5.28.5 修补了多个关键安全漏洞，覆盖命令注入、参数注入、缓存投毒和 TOCTOU 窗口。

### 11.1 H-7：提权命令行参数注入

**问题**：View-AdminElevation.ps1 和 View-ProMode.ps1 在重启提权时，将语言参数和路径参数直接拼接到命令行，未做校验，存在命令行元字符注入风险。

**修复**：新增两个校验函数：

- **Test-AuroraLanguageSafe**：严格白名单，仅允许 "CHS" 或 "ENG"
- **Test-AuroraPathSafe**：拒绝包含 `[<>&|\`"$]` 元字符的路径，规范化路径验证绝对路径，允许不存在（令牌文件可能尚未生成）

校验链：View-AdminElevation.ps1 被 AURORA-AnalyzerLauncherGUI.ps1 dot-source 引入，暴露校验函数给所有后续脚本。View-ProMode.ps1 通过 Restart-WithAdmin（定义在 View-AdminElevation.ps1）间接使用校验。

### 11.2 H-6：Invoke-Expression 命令注入与缓存投毒

**问题**：AURORA-SmartEngine.ps1 三处使用 Invoke-Execution 执行 JSON 配置中的命令字符串，攻击者可通过篡改 JSON 注入任意命令。同时 SecurityModule.ps1 的完整性校验缓存存在 TOCTOU 窗口。

**修复**：

- **Test-AuroraCommandSafe**：最大命令长度 8192 字符，正则黑名单覆盖命令执行（Invoke-Expression/iex/Invoke-WebRequest/Invoke-Command/Start-Job/Start-Process）、网络（DownloadString/Net.WebClient/HttpClient/Socket/TcpClient）、持久化（Register-ScheduledTask/New-Service）、反射注入（Reflection.Assembly/Add-Type）、编码绕过（-EncodedCommand/FromBase64String）、进程注入（PowerShell -Command/cmd /c/certutil/bitsadmin/mshta）、WMI 绕过、注册表篡改、环境变量篡改（AURORA_PublicKeyXml/AURORA_SessionSalt/AURORA_AesSalt/AURORA_TOKEN_PATH/AURORA_HASH_PATH）
- **Invoke-AuroraSafeCommand**：替换 Invoke-Expression 为 `[ScriptBlock]::Create($CommandStr)` + `& $sb`（当前作用域，保留 syncHash 和模块访问），审计日志记录到 `%LOCALAPPDATA%\AURORA\Logs\command_audit.log`（时间戳/PID/命令长度/SHA256/200 字符预览）
- **三处替换**：pre_check（521 行）、command（742 行）、rollback_command（976 行）
- **_integrityCacheDuration = TimeSpan.Zero**：消除完整性校验缓存 TOCTOU 窗口，每次 CheckIntegrity 重新计算哈希

### 11.3 编码修复

为 View-AdminElevation.ps1、View-ProMode.ps1、AURORA-AnalyzerLauncherGUI.ps1 添加 UTF-8 BOM，修复中文 Windows 上的解析问题。

### 11.4 影响范围

View-AdminElevation.ps1、View-ProMode.ps1、AURORA-AnalyzerLauncherGUI.ps1、AURORA-SmartEngine.ps1、AURORA-SecurityModule.ps1。

## 13. 已知限制

### 13.1 远程会话下的 GPU 后端禁用

在 RDP 远程会话或 VM 环境下，GPU 后端（ShaderEffect 和 DWM Acrylic）被强制禁用，回退到 RTB 软件模糊。这是刻意的安全设计（RDP 无法正确渲染 Acrylic），但会导致远程会话下的玻璃材质视觉效果略有差异。

### 13.2 动效归一化的 45fps 基准

timeScale 分母从 16.667 改为 22.222 是基于 DispatcherTimer 在 Render 优先级下的实际平均帧率。在极端高刷新率（240Hz+）显示器上，归一化后的动效速度可能与设计预期略有差异，但视觉一致性优于此前。

### 13.3 CLI 适配层的 Read-Host 阻塞

AURORA-SmartEngine-CLI.ps1 的主线程轮询使用 Read-Host 阻塞等待用户输入。在 SmartEngine 执行长时间任务期间，主线程仍可轮询 syncHash 状态并打印进度，但无法同时接受多个输入。

### 13.4 安全校验的性能开销

_integrityCacheDuration = TimeSpan.Zero 导致每次 CheckIntegrity 重新计算所有文件哈希。在文件较多时可能带来可感知的启动延迟，但这是安全关键路径的必要开销。
