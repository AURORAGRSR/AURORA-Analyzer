## 1. Version Overview

V1.5.28.5 is an AURORA-Analyzer release that builds upon the V1.5.28.0 view system reshaping with a rendering mechanism refactor and console mode usability upgrade. This update centers on seven core areas:

1. **Rendering Mechanism Refactor and Refresh Rate Adaptation**: Introduces a six-in-one GPU utilization optimization mechanism (startup probing, dynamic tiering, render layer subscription, backend fallback chain, frequency adaptation, remote session detection), and normalizes animation frame rates based on the screen's actual refresh rate, significantly improving GUI fluidity and responsiveness
2. **Console Mode GUI/CLI Dual-Mode Compatibility**: Builds the AURORA-SmartEngine-CLI.ps1 adaptation layer, enabling SmartEngine to complete all five GUI wait points (elevation, authorization, CSV export confirmation, elevation remediation, main menu loop) in a pure console environment
3. **SMART SLI Smart Mode Invocation Bridge**: Console mode gains the ability to invoke Smart Mode, bringing automated smart repair to console users
4. **PRO Mode Control Entrance Animation Fix**: Upgrades the fixed 1500ms fallback timer to a dynamic calculation formula, eliminating the sudden animation jump on trailing controls
5. **History View and Solution View Multiple Optimizations**: Fixes hit detection mechanism, adds solution entry point, optimizes bottom buttons staggered entrance, optimizes undo manager
6. **Main Window and Global Visual Detail Optimization**: Adjusts language list order, optimizes splash text layout, UWP status text sync, modal dialog mask animations and visual effects
7. **Extensive Security Updates**: Patches privilege escalation command line parameter injection, Invoke-Expression command injection and cache poisoning, integrity check TOCTOU window, and other critical vulnerabilities

In rendering optimization, V1.5.28.5 establishes a complete GPU utilization optimization chain:

| Optimization Mechanism | Description |
|------------------------|-------------|
| Startup Probing | Probes GPU vendor, VRAM, D3D9Ex support, ShaderEffect availability, remote session state via MaterialCapabilities.Probe |
| Dynamic Tiering | Dynamically classifies into Eco/Balanced/Performance/Extreme tiers based on RenderCapability.Tier and hardware probe results |
| Render Layer Subscription | CompositionTarget.Rendering subscribes on first Composer registration, unsubscribes when last Composer unregisters, preventing idle consumption |
| Backend Fallback Chain | ShaderEffect HLSL gaussian blur → RtbBlurBackend software blur, forced software fallback on remote sessions |

| Remote Session Detection | Dual-path detection (GetSystemMetrics + WTSQuerySessionInformation), forces GPU backend disable on RDP |

In animation normalization, V1.5.28.5 corrects the original 60fps normalization benchmark (timeScale denominator 16.667) to 45fps (denominator 22.222), matching the actual average frame rate that DispatcherTimer achieves at Render priority due to Dispatcher queue scheduling jitter, making visual speed consistent with design intent:

For console mode, V1.5.28.5 implements the complete smart repair flow in a pure console environment via the AURORA-SmartEngine-CLI.ps1 three-layer architecture (thread-safe syncHash + background Runspace executing SmartEngine + main thread polling responding to GUI events).

## 2. Rendering Mechanism Refactor and Refresh Rate Adaptation

V1.5.28.5 comprehensively refactors the graphics rendering pipeline, establishing a six-in-one GPU utilization optimization mechanism, and normalizes animation frame rates based on the screen's actual refresh rate.

### 2.1 Startup Probing

App.xaml.cs executes a three-phase probe at application startup:

- **Render Mode Selection**: `RenderOptions.ProcessRenderMode = RenderMode.Default`, letting WPF decide (hardware preferred, software fallback). `HardwareOnly` is deliberately avoided as it throws on machines without GPU drivers
- **Initial Tier**: `int initialTier = RenderCapability.Tier >> 16` (0=software rendering, 1=2D hardware, 2=advanced hardware), subscribing to `RenderCapability.TierChanged` for runtime tier changes
- **Hardware Capability Probe**: Calls `AuroraRenderEngine.DetectPerformanceTierAndReturn()` and `MaterialCapabilities.Current`, obtaining full diagnostics: cores, gpuName, gpuVendor, d3d9ex, gpuVramMB, gpuScore, recommendedBackend

MaterialCapabilities.Probe probes d3dcompiler_47.dll (LoadLibrary) and Direct3DCreate9Ex (D3D9Ex device support) via P/Invoke, and performs dual-path remote session detection.

### 2.2 Dynamic Tiering

Based on probe results, AURORA-Analyzer classifies into four performance tiers:

| Tier | Trigger Condition | Blur Capture Frequency | Starfield Redraw |
|------|-------------------|------------------------|------------------|
| Eco | RenderCapability.Tier == 0 or remote session | 100ms (10fps) | Degraded |
| Balanced | Low-end GPU or insufficient VRAM | 66ms (15fps) | Standard |
| Performance | Mainstream GPU | 50ms (20fps) | Standard |
| Extreme | High-end GPU | 33ms (30fps) | Full effects |

### 2.3 Render Layer Subscription

AuroraMaterialPipeline adopts a lazy subscription pattern:

- Auto-subscribes to `CompositionTarget.Rendering` on first AuroraMaterialComposer registration
- Unsubscribes when the last Composer unregisters, preventing idle consumption
- `_isRenderingSubscribed` flag ensures subscription state consistency

This mechanism ensures that when all glass material components are invisible, the rendering callback stops entirely, avoiding meaningless per-frame computation.

### 2.4 Backend Fallback Chain

The blur backend uses a three-level fallback chain (SelectBlurBackend):

1. **Tier == 0 (software rendering) → RtbBlurBackend (forced)**: Under software rendering, ShaderEffect HLSL PS 3.0 runs on CPU, slower than RTB+BlurEffect
2. **Tier >= 1 → ShaderEffectBackend (if available)**: HLSL PS 3.0 GPU 9-tap gaussian blur, depends on d3dcompiler_47.dll and AuroraBlurShaderEffect compile success; falls through if unavailable
3. **Final fallback → RtbBlurBackend**: Always available on Win7+

`ReloadBlurBackend()` triggers on GPU driver crash, power mode switch, or remote session connect/disconnect — disposes old backend, re-selects, resets background sample cache to force next-frame re-capture.

### 2.5 Frequency Adaptation

`GetBackgroundCaptureThrottleMs()` dynamically returns throttle values based on current tier:

```
Tier == 0 (software rendering) → 100ms (10fps)
PerformanceTier.Eco             → 66ms (15fps)
PerformanceTier.Balanced        → 50ms (20fps)
Performance / Extreme           → 33ms (30fps)
```

This value is used by `CaptureBackgroundIfNeeded` to throttle background sample capture, avoiding expensive per-frame `RTB.Render`.

### 2.6 Remote Session Detection

MaterialCapabilities.DetectRemoteSession uses dual-path detection:

- **Fast path**: `GetSystemMetrics(SM_REMOTESESSION = 0x1000)` via user32.dll P/Invoke
- **Accurate path**: `ProcessIdToSessionId` → `WTSQuerySessionInformation(WTSConnectState)` → reads 4-byte integer state. Only `WTSActive=0` is treated as a true local session; all other states (WTSConnected=1, WTSDisconnected=4, WTSDown=7, etc.) count as remote
- **Conservative on failure**: Assumes non-remote on detection failure (avoids false-disabling GPU backends)

When remote session detected: forces disable DWM backend (RDP cannot render Acrylic), `SupportsShaderEffect = false`, forces RtbBlurBackend software blur fallback.

### 2.7 Animation Frame Rate Normalization (45fps Benchmark)

V1.5.28.5 corrects the animation normalization benchmark. The original code set the timeScale denominator to 16.667 (60fps theoretical), but DispatcherTimer at Render priority experiences Dispatcher queue scheduling jitter, yielding an actual average frame rate of approximately 45fps. The benchmark mismatch caused animations to appear ~33% faster than design intent.

The fix changes the timeScale denominator from 16.667 to 22.222 in three animation controls:

| Control | File | Modified Location |
|---------|------|-------------------|
| AuroraButton | AuroraButton.cs:725 | Hover/color/glow/focus/press/spring/loading/ambient/magnetic |
| AuroraTaskHUD | AuroraTaskHUD.cs:257 | Breathing/icon/transition |
| AuroraProgressBar | AuroraProgressBar.cs:202 | Progress smoothing/glow position/particle age |

Normalized timeScale values per refresh rate: 60Hz → 0.75, 120Hz → 0.375, 160Hz → 0.281, 320Hz → 0.141. Eco mode uses 1.0 timeScale + 33ms throttle, no normalization.

## 3. Console Mode GUI/CLI Dual-Mode Compatibility

V1.5.28.5 builds the AURORA-SmartEngine-CLI.ps1 adaptation layer, enabling SmartEngine to complete the full smart repair flow in a pure console environment.

### 3.1 Three-Layer Architecture

AURORA-SmartEngine-CLI.ps1 adopts a three-layer design:

1. **Pre-create thread-safe syncHash**: `$global:syncHash = [hashtable]::Synchronized(@{})`, LogOutput uses `[System.Collections.ArrayList]::Synchronized(...)`, ensuring cross-Runspace visibility
2. **Background Runspace executes SmartEngine.ps1**: Preserves original logic unmodified, launched asynchronously via `$ps.BeginInvoke()`
3. **Main thread polls syncHash**: Main thread loops polling, using `Read-Host` to respond to all GUI events

### 3.2 Five GUI Wait Points

SmartEngine.ps1 has five blocking wait points in its execution flow; the CLI adaptation layer takes over each:

| # | SmartEngine Wait Point | syncHash Keys | CLI Response |
|---|------------------------|---------------|--------------|
| 1 | Pre-elevation wait (lines 299-309) | RequiresElevation / ElevationAuthorized | Read-Host + launch admin process |
| 2 | Authorization EventWaitHandle wait (line 425) | AuthorizationEventName + Authorized | Read-Host + Set event |
| 3 | CSV export log confirmation (lines 1187-1194) | RequiresUserInput / UserInput | Read-Host y/n choice |
| 4 | Catch-branch elevation remediation (lines 687-697) | Same as #1 | Same as #1 |
| 5 | Main menu event loop (lines 1618-1720) | IsHostAlive / UserInput / Authorized / PendingCommand | Read-Host menu selection |

### 3.3 Polling State Machine

The CLI adaptation layer's main loop contains a complete polling state machine:

- **4.3 Elevation request handling**: Detects `RequiresElevation == $true`, prompts user, sets `ElevationAuthorized = $true/false`, resets `RequiresElevation = $false`, sleeps 5s waiting for SmartEngine to call `Invoke-SafeExit`
- **4.4 Authorization request handling**: Detects `RequiresAuthorization -eq $true -and $null -eq $Authorized`, displays `PendingCommand`, 's' key sets `Authorized = $false`
- **4.5 CSV export confirmation**: Detects `RequiresUserInput -eq $true`, prompts "[y] use exported logs [n] rescan"
- **4.7 Menu input handling**: 'm' input reprints menu directly in CLI without SmartEngine interaction

### 3.4 Startup Security

The CLI adaptation layer performs RSA token verification + parent process verification at startup. The `-FromPRO` / `-GUI_Mode` switches alone are not trusted (any user can add them) — `syncHash` must already exist in the global scope for execution to proceed.

### 3.5 Integration Points

AURORA-SmartEngine-CLI.ps1 integrates into AURORA-AnalyzerPRO.ps1's `-ConsoleMode` branch, accessible via both the performance upgrade dialog and MainForm View 2 console buttons.

### 3.6 Encoding and Fixes

The CLI adaptation layer adds UTF-8 BOM to resolve Chinese encoding errors on Chinese Windows, adjusts AddScript calls, reformats elseif statements, and modifies string escaping. Fixed issues including execution results not printing (premature status detection + Read-Host thread blocking), manual 'm' refresh required after privilege cancellation (missed state changes), and duplicate menu printing (redundant logs + unhandled 'm' command).

## 5. PRO Mode Control Entrance Animation Time Jump Fix

### 5.1 Issue

In ProModeView.PlayControlEnterAnimation's 16 controls, trailing controls (ExitButton delay 1120ms, MinimizeButton delay 1200ms) had their main animation (450ms) not yet completed when the fixed 1500ms fallback timer fired and force-reset ScaleTransform to terminal state, causing a visual "sudden acceleration" jump.

### 5.2 Root Cause

The fixed 1500ms fallback timer was designed for V1.5.28.0's smaller control count. After ProModeView grew to 16 controls, the last control's animation completion time became (16-1)×80 + 450 + 525 = 2175ms, far exceeding 1500ms.

### 5.3 Fix

The fallback timer was changed to a dynamic calculation formula:

```
fallbackMs = (tiles.Count - 1) * staggerMs + durationMs + bounceDurationMs + 100
```

For ProModeView's 16 controls: (16-1) × 80 + 450 + 525 + 100 = **2275ms**, ensuring all control animations complete before fallback triggers.

### 5.4 Parameters

| Parameter | Value | Description |
|-----------|-------|-------------|
| staggerMs | 80 | Adjacent tile stagger delay |
| durationMs | 450 | Main animation duration (0→1.07 Scale + 0→1 Opacity + 100→0 Y) |
| bounceDurationMs | 525 | Jelly convergence duration (1.07→1.0) |
| Buffer | 100ms | Dispatcher scheduling jitter tolerance |

### 5.5 Impact Scope

ProModeView.xaml.cs PlayControlEnterAnimation fallback timer calculation logic.

## 6. History View Hit Detection Mechanism Fix

### 6.1 Health Score Calculation Fix (Integer Division Truncation)

**Issue**: ExportHistoryService.ComputeHealthScore used integer division `totalIssues * 100 / totalEvents`. When totalIssues was small (e.g., 1 warning) and totalEvents was large (e.g., 200), integer division truncation resulted in a zero deduction, incorrectly returning a health score of 100.

**Fix**: Extracted as a public static method using floating-point arithmetic:

```csharp
public static int ComputeHealthScore(int critical, int error, int warning, int totalEvents)
{
    if (totalEvents <= 0) return 100;
    int totalIssues = critical * 3 + error * 2 + warning;
    double score = 100.0 - (double)totalIssues * 100.0 / (double)totalEvents;
    return Math.Max(0, (int)Math.Round(score));
}
```

Weights: critical=3, error=2, warning=1. HistoryMatchService calls the same method to ensure formula consistency.

### 6.2 Scan Window Dynamic Expansion

**Issue**: HistoryMatchService used a fixed 24h scan window. When the exported log's time range exceeded 24h, freshly exported logs failed to match due to being outside the window.

**Fix**: Added ComputeScanWindowHours method to dynamically calculate the window:

- Default 24h
- Takes max(24h, span from DateRange start date to now)
- Capped at 720h (30 days)

Supports both single date (yyyyMMdd) and date range (start-end) formats. When DateRange span exceeds 24h, the window auto-expands to cover the export time range.

### 6.3 Impact Scope

ExportHistoryService.cs ComputeHealthScore, HistoryMatchService.cs ComputeScanWindowHours and Detect call chain.

## 11. Security Update Batch Hardening

V1.5.28.5 patches multiple critical security vulnerabilities, covering command injection, parameter injection, cache poisoning, and TOCTOU windows.

### 11.1 H-7: Privilege Escalation Command Line Parameter Injection

**Issue**: View-AdminElevation.ps1 and View-ProMode.ps1 directly concatenated language and path parameters to the command line during restart elevation, without validation, posing command line metacharacter injection risk.

**Fix**: Added two validation functions:

- **Test-AuroraLanguageSafe**: Strict whitelist, only allows "CHS" or "ENG"
- **Test-AuroraPathSafe**: Rejects paths containing `[<>&|\`"$]` metacharacters, normalizes path to verify absolute path, allows non-existence (token files may not yet exist)

Validation chain: View-AdminElevation.ps1 is dot-sourced by AURORA-AnalyzerLauncherGUI.ps1, exposing validators to all subsequently loaded scripts. View-ProMode.ps1 uses validation indirectly via Restart-WithAdmin (defined in View-AdminElevation.ps1).

### 11.2 H-6: Invoke-Expression Command Injection and Cache Poisoning

**Issue**: AURORA-SmartEngine.ps1 used Invoke-Expression in three places to execute command strings from JSON configuration, allowing attackers to inject arbitrary commands via tampered JSON. SecurityModule.ps1's integrity check cache also had a TOCTOU window.

**Fix**:

- **Test-AuroraCommandSafe**: Max command length 8192 chars, regex blacklist covering command execution (Invoke-Expression/iex/Invoke-WebRequest/Invoke-Command/Start-Job/Start-Process), network (DownloadString/Net.WebClient/HttpClient/Socket/TcpClient), persistence (Register-ScheduledTask/New-Service), reflection injection (Reflection.Assembly/Add-Type), encoding bypass (-EncodedCommand/FromBase64String), process injection (PowerShell -Command/cmd /c/certutil/bitsadmin/mshta), WMI bypass, registry tampering, environment variable tampering (AURORA_PublicKeyXml/AURORA_SessionSalt/AURORA_AesSalt/AURORA_TOKEN_PATH/AURORA_HASH_PATH)
- **Invoke-AuroraSafeCommand**: Replaces Invoke-Expression with `[ScriptBlock]::Create($CommandStr)` + `& $sb` (current scope, preserving syncHash and module access), audit log to `%LOCALAPPDATA%\AURORA\Logs\command_audit.log` (timestamp/PID/command length/SHA256/200-char preview)
- **Three replacement sites**: pre_check (line 521), command (line 742), rollback_command (line 976)
- **_integrityCacheDuration = TimeSpan.Zero**: Eliminates TOCTOU window, every CheckIntegrity recomputes file hashes

### 11.3 Encoding Fix

Added UTF-8 BOM to View-AdminElevation.ps1, View-ProMode.ps1, and AURORA-AnalyzerLauncherGUI.ps1 to fix parsing issues on Chinese Windows.

### 11.4 Impact Scope

View-AdminElevation.ps1, View-ProMode.ps1, AURORA-AnalyzerLauncherGUI.ps1, AURORA-SmartEngine.ps1, AURORA-SecurityModule.ps1.

## 13. Known Limitations

### 13.1 GPU Backend Disable on Remote Sessions

Under RDP remote sessions or VM environments, GPU backends (ShaderEffect and DWM Acrylic) are forcibly disabled, falling back to RTB software blur. This is a deliberate safety design (RDP cannot properly render Acrylic), but results in slightly different glass material visuals under remote sessions.

### 13.2 45fps Benchmark for Animation Normalization

The timeScale denominator change from 16.667 to 22.222 is based on DispatcherTimer's actual average frame rate at Render priority. On extreme high refresh rate (240Hz+) displays, normalized animation speed may differ slightly from design intent, but visual consistency is superior to the previous approach.

### 13.3 Read-Host Blocking in CLI Adaptation Layer

AURORA-SmartEngine-CLI.ps1's main thread polling uses Read-Host blocking to wait for user input. During long-running SmartEngine tasks, the main thread can still poll syncHash status and print progress, but cannot accept multiple inputs simultaneously.

### 13.4 Performance Overhead of Security Validation

_integrityCacheDuration = TimeSpan.Zero causes every CheckIntegrity call to recompute all file hashes. With many files, this may introduce noticeable startup latency, but this is a necessary cost for security-critical paths.
