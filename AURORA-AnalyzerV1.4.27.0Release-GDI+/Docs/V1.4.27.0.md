## 1. 版本概述

V1.4.27.0 是 AURORA-Analyzer 自项目启动以来最大的一次架构升级版本。整个用户界面层从基于 PowerShell 脚本直接创建 WinForm GDI+ 控件的传统模式，完全迁移至 Windows Presentation Foundation 框架。这一迁移并非简单的技术栈替换，而是涉及渲染管线、事件模型、控件生命周期、资源管理策略和动画系统五个维度的全面重构。

V1.3.26.7 及之前版本的核心架构是 PowerShell 脚本通过 Add-Type 动态编译 C# Windows.Forms 类来创建 UI 控件，所有渲染工作由 GDI+ 在 CPU 上完成。这种模式在项目早期阶段提供了快速原型开发的优势，但随着 UI 复杂度的提升——毛玻璃背景、星空粒子、17 种按钮动效、UWP 风格视图切换——GDI+ 的 CPU 渲染瓶颈和 WinForms 的单线程 STA 消息泵模型成为了性能天花板。

V1.4.27.0 将 UI 层完全替换为 C# 5.0 编译的 WPF 控件库，利用 WPF 的保留模式渲染管线、GPU 加速的 DirectX 底层、数据绑定驱动的 MVVM 架构，以及 Storyboard + CompositionTarget.Rendering 双驱动动画系统，实现了渲染性能的数十倍提升和代码架构的清晰分层。

尽管底层渲染引擎发生了根本性变化，V1.4.27.0 保持了与 V1.3.x 系列相同的 PowerShell 脚本接口、syncHash 同步机制、命令行参数和业务逻辑流程。现有的 PowerShell 脚本引擎无需任何修改即可在新架构上运行。

## 2. 架构变更

V1.4.27.0 的架构变更涉及五个核心维度，每一项都是从旧模式到新模式的根本性转变。

### 2.1 事件模型：从 WinForm 事件驱动到 WPF MVVM 模式

在 V1.3.x 中，UI 交互逻辑直接嵌入在 PowerShell 脚本中，通过 `$Button.Add_Click({ ... })` 方式注册事件处理器。业务逻辑与 UI 代码紧密耦合，同一段脚本中可能同时包含数据库查询逻辑和按钮颜色设置代码。这使得单元测试几乎不可能，代码复用率极低。

V1.4.27.0 引入了 MVVM 架构，将 UI 交互逻辑与业务逻辑彻底解耦。ViewModel 通过实现 INotifyPropertyChanged 接口暴露可绑定的属性和命令，View 层仅负责声明式地绑定这些属性，不再包含任何业务逻辑。Service 层封装了所有业务操作，ViewModel 通过依赖注入获取 Service 实例，进一步降低了耦合度。

### 2.2 控件创建：从 PowerShell 脚本创建 UI 到 C# 5.0 编译控件库

在 V1.3.x 中，所有 UI 控件通过 PowerShell 的 Add-Type 在运行时动态编译 C# 代码创建。这种方式下，每次启动都需要重新编译所有控件类，启动时间随控件数量线性增长。此外，Add-Type 编译的代码无法使用 NuGet 包、无法进行预编译优化、无法享受 IDE 的智能提示和重构支持。

V1.4.27.0 将所有 UI 控件提取为独立的 C# 5.0 类库项目，预编译为 DLL。启动时直接加载预编译的程序集，启动时间大幅缩短。控件库在 Visual Studio 中开发，享受完整的智能提示、静态分析和重构工具支持。C# 5.0 的语言版本选择是为了保持与 PowerShell 5.1 的兼容性，确保编译后的 DLL 可以在 PowerShell 5.1 的 CLR 环境中加载。

### 2.3 并行模型：从单 Runspace 到 RunspacePool 并行

V1.3.x 使用单个 PowerShell Runspace 运行所有后台任务。当后台任务正在执行耗时操作时，UI 线程可能因等待 syncHash 同步而出现卡顿。

V1.4.27.0 引入了 RunspacePool 并行模型。PowerShellHost Service 管理一个 RunspacePool，最大并发数根据当前性能等级动态调整。每个后台任务从池中获取一个独立的 Runspace，任务完成后 Runspace 归还池中复用。UI 线程通过 syncHash 与 Runspace 通信，完全不阻塞 WPF 的渲染线程。

### 2.4 渲染管线：从 GDI+ CPU 渲染到 WPF GPU 加速渲染

这是最根本的性能提升来源。GDI+ 使用 CPU 进行所有 2D 绘制操作，包括抗锯齿、透明度混合、渐变填充等。当 UI 包含大量半透明效果、模糊背景、粒子动画时，CPU 渲染的帧率会急剧下降。

WPF 的渲染管线基于 DirectX 9/11，所有绘制操作由 GPU 执行。这意味着大量的半透明叠加、高斯模糊、渐变填充等操作可以在 GPU 上并行处理，释放 CPU 资源用于业务逻辑计算。在 V1.4.27.0 中，毛玻璃背景的实时模糊、星空粒子的 60fps 渲染、按钮的渐变动效等，全部由 GPU 加速，CPU 占用率显著降低。

### 2.5 语言引擎：从双语言引擎文件到单引擎 + LanguageService

V1.3.x 使用 CHSPRO 和 ENGPRO 两套独立的引擎文件来支持中英文切换。这导致引擎逻辑的每次修改都需要在两个文件中同步进行，维护成本高，且容易出现中英文版本行为不一致的问题。

V1.4.27.0 将引擎文件合并为单一引擎，所有 UI 文本通过 LanguageService 在运行时动态切换。LanguageService 维护一个资源字典，每个文本键对应中文和英文两个值。WPF 的 DynamicResource 机制确保切换语言时所有绑定的 UI 文本自动更新，无需重启应用。

## 3. MVVM 架构

V1.4.27.0 的 MVVM 架构分为四个清晰的层次，每一层都有明确的职责边界。

### 3.1 View 层

View 层由四个 WPF Window/UserControl 组成，负责纯声明式的 UI 布局和样式定义。

| 视图 | 类型 | 职责 |
|------|------|------|
| SplashScreenView | Window | 启动闪屏，展示加载进度和不规则透明窗口 |
| MainFormView | Window | 主界面，包含按钮面板、控制台输出、星空背景和毛玻璃效果 |
| ProModeView | Window | 专业模式面板，提供高级诊断功能的入口 |
| UndoViewerView | Window | 撤销查看器，展示历史操作记录和回滚选项 |

每个 View 的 XAML 文件仅包含控件声明、样式绑定和动画触发器定义，不包含任何业务逻辑代码。View 通过 DataContext 绑定到对应的 ViewModel，所有交互通过 Command 绑定和 Data Binding 实现。

### 3.2 ViewModel 层

ViewModel 层是 View 和 Service 之间的桥梁，负责将 Service 层的业务数据转换为 View 层可直接绑定的形式。

每个 ViewModel 实现 INotifyPropertyChanged 接口，在属性值变化时自动通知 View 更新。所有 ViewModel 继承自一个统一的 ViewModelBase 基类，该基类封装了 PropertyChanged 事件的触发逻辑和属性变更的简化调用。

ViewModel 之间的导航通过 NavigatorService 实现，支持视图切换时的动画编排。ViewModel 不直接引用 View 实例，而是通过 NavigatorService 请求视图切换，保持了 View 和 ViewModel 的完全解耦。

### 3.3 Service 层

Service 层是业务逻辑的核心承载者，包含 14 个独立的服务类，每个服务类封装一个单一职责的业务领域。

| 服务 | 职责 |
|------|------|
| PowerShellHost | 管理 RunspacePool，执行 PowerShell 脚本，通过 syncHash 与 UI 线程通信 |
| RenderEngine | 封装 WPF 渲染管线的底层操作，管理 CompositionTarget 渲染事件 |
| ElevationService | 处理 UAC 提权请求，管理提权令牌的生成和验证 |
| SecurityService | 驱动完整性校验和令牌验证流程 |
| LanguageService | 管理多语言资源字典，运行时动态切换语言 |
| NavigatorService | 管理 View 之间的导航，编排视图切换动画 |
| AnimationService | 协调 Storyboard 和帧级动画的启动、停止和状态查询 |
| ThemeService | 管理应用主题，提供极光色采样和呼吸调制 |
| SettingsService | 持久化和读取用户配置，包括性能等级设置 |
| TelemetryService | 结构化遥测数据的记录、持久化和上报 |
| SessionService | 会话状态的保存和恢复，包含 AgeInDays 追踪 |
| WatchdogService | 看门狗监控，检测异常进程退出并触发安全清理 |
| IntegrityGuardService | 完整性校验，检测文件篡改和未授权修改 |
| LogService | 结构化日志输出，支持分级过滤和文件持久化 |

### 3.4 动画层

动画层是 V1.4.27.0 在标准 MVVM 之外新增的第四层，专门处理复杂的 UI 动画逻辑。

| 组件 | 职责 |
|------|------|
| AnimationHelper | 提供动画辅助方法，如缓动函数查找、动画状态查询、帧率归一化计算 |
| UwpEasingCurves | 实现 UWP 风格的缓动曲线（CubicEase、BackEase、CircleEase 等），供 Storyboard 调用 |
| AuroraCustomEasing | 实现 Aurora 自定义缓动曲线，包括 iOS 风格的二次回弹曲线和呼吸式缓动 |

## 4. 毛玻璃材质系统

AuroraGlassMaterial 是 V1.4.27.0 中最复杂的视觉系统，实现了四层渲染管线的高性能毛玻璃效果。该系统的设计目标是：在视觉上呈现与 Windows Acrylic 材质一致的通透感和层次感，同时在性能上不拖累整体渲染帧率。

### 4.1 四层渲染管线

毛玻璃效果通过四层叠加实现，从底层到顶层依次为：

第一层，双层投影。底层使用大半径的柔光投影模拟玻璃材质的光晕扩散效果，上层使用小半径的锐利投影增强玻璃边界的立体感。两层投影的颜色和透明度根据当前极光主题色动态调整，使得玻璃材质与整体 UI 的色调保持协调。

第二层，真模糊背景。这是毛玻璃效果的核心。系统通过 RenderTargetBitmap 捕获玻璃控件背后区域的视觉内容，然后应用 GaussianBlurEffect 进行模糊处理，最后将模糊结果作为背景填充。模糊半径在 12 到 24 像素之间，根据窗口大小动态调整，确保在不同分辨率下都有合适的模糊度。

第三层，玻璃主体渐变。在模糊背景之上叠加一层半透明的线性渐变，模拟玻璃材质的光线折射效果。渐变的起止色和透明度根据极光主题色动态采样，使得玻璃材质随主题色变化而呈现不同的色调。

第四层，表层覆盖。最上层是一层微噪点纹理叠加，用于模拟磨砂玻璃的颗粒感。噪点纹理使用 128×128 像素的固定种子生成，确保每次启动时噪点图案一致，不会出现闪烁。

### 4.2 30fps 模糊捕获节流

实时模糊背景的最大性能瓶颈是 RenderTargetBitmap 的捕获操作，它需要将整个视觉树渲染到一张位图中。如果每帧都执行捕获，即使 GPU 能够承受，内存带宽也会成为瓶颈。

V1.4.27.0 实现了智能节流机制：模糊背景以 30fps 的固定频率捕获和更新，而非跟随 WPF 的 60fps 渲染循环。这意味着模糊捕获的频率降低了一半，视觉效果几乎没有可感知的差异——因为模糊背景本身的变化就比较缓慢。更重要的是，当窗口中没有任何毛玻璃控件处于可见状态时，系统完全跳过 RenderTargetBitmap 的捕获操作，将节省的资源全部释放给其他渲染任务。

### 4.3 笔刷缓存池

WPF 的渐变画刷和颜色画刷在频繁创建时会触发大量的托管堆分配和小对象回收，导致 GC 压力增大。V1.4.27.0 引入了笔刷缓存池机制：所有常用的渐变画刷和颜色画刷在首次创建后立即调用 Freeze 方法冻结为不可变对象，并缓存到字典中。后续使用时直接从缓存池获取，不需要重新分配内存。

冻结后的画刷对象变为 Frozen 状态，WPF 渲染引擎可以对其进行特殊优化——因为不可变对象不需要线程同步、不需要克隆、可以直接在 GPU 内存中共享。这意味着在每一帧的渲染过程中，毛玻璃系统的所有画刷操作都是零 GC 分配的。

### 4.4 微噪点纹理

磨砂玻璃的颗粒感通过一个 128×128 像素的微噪点纹理实现。纹理使用固定种子生成，确保每次启动时噪点图案一致。所有毛玻璃控件共享同一个噪点纹理实例——通过 Lazy 模式初始化，在首次访问时创建，之后所有控件引用同一个实例。这避免了为每个玻璃控件重复生成噪点纹理的内存浪费。

噪点纹理以极低的透明度叠加在玻璃主体之上，只有在近距离观察时才能察觉到微妙的颗粒质感。这种细节处理是 Aurora 视觉设计语言的核心元素之一，在 V1.3.x 时代由于 GDI+ 的性能限制无法实现。

## 5. 星空背景

AuroraStarfield 是主界面背景的星空粒子系统，在 V1.4.27.0 中从 GDI+ 的 CPU 逐像素绘制完全迁移到 WPF 的 GPU 加速渲染。

### 5.1 CompositionTarget.Rendering 60fps vsync 驱动

星空系统使用 WPF 的 CompositionTarget.Rendering 事件驱动每帧更新。该事件在每个垂直同步信号到来时触发，与显示器的刷新率同步。在 60Hz 显示器上为 60fps，在 120Hz 显示器上为 120fps。帧更新的实际计算（粒子位置更新、颜色插值、新粒子生成）在 CPU 上完成，但所有绘制操作——粒子的圆点渲染、透明度混合、发光效果——由 GPU 并行处理。

### 5.2 帧率归一化

直接在每帧中按固定步长移动粒子会导致一个问题：在 120Hz 显示器上，粒子移动速度会变成 60Hz 显示器上的两倍，造成动画快进。V1.4.27.0 使用 `Stopwatch` 测量真实的帧间隔时间，以 30fps 为基准进行帧率归一化。所有与时间相关的计算（粒子位移、颜色渐变、透明度衰减）都乘以 `deltaTime / (1.0 / 30.0)` 的归一化因子，确保在不同刷新率的显示器上，动画的感知速度完全一致。

### 5.3 预生成极光画刷缓存池

星空中的极光粒子使用 RadialGradientBrush 实现从中心亮白到边缘透明的渐变效果。与毛玻璃系统的笔刷缓存类似，所有极光画刷在首次创建后冻结并缓存。缓存池按粒子类型（恒星、行星、流星、极光带）和颜色方案（蓝绿、紫粉、青蓝）组织，在运行时通过索引快速查找。

### 5.4 真实时间步进驱动

粒子的运动计算使用 `Stopwatch` 获取的真实时间步进，而非依赖帧计数。这意味着即使某一帧因为 UI 线程繁忙而延迟渲染，下一帧的粒子位置会基于真实流逝的时间来计算，补上跳过的运动距离。这与渲染帧率完全解耦，确保了动画的时间准确性。

## 6. 按钮系统

AuroraButton 是 V1.4.27.0 中定制化程度最高的控件，完整保留了 V1.3.x 时代积累的 17 种动效细节，并在 WPF 中进行了 GPU 加速重构。

### 6.1 17 种动效细节

按钮的 17 种动效通过 WPF 的 Trigger 和 VisualState 机制实现，涵盖正常、悬停、按下、释放、禁用、聚焦六种状态下的视觉效果变化。这些动效包括：悬停时的背景渐变偏移、边框发光扩散、文字阴影出现、图标微缩放、内阴影加深、外光晕扩散、按下时的背景压缩、边框收缩、文字下沉、图标缩小、内阴影扁平化、释放时的弹性恢复、背景回弹、边框回弹、文字回弹、图标回弹、外光晕消散。

在 V1.3.x 中，这些动效通过多个 WinForms Timer 和 GDI+ 逐帧绘制实现，每帧需要完整重绘按钮的全部像素。在 V1.4.27.0 中，这些动效通过 WPF 的 Storyboard 和属性动画实现，GPU 仅处理变化的像素区域，性能提升显著。

### 6.2 极光环境色注入

按钮的背景渐变和边框发光颜色不是固定的，而是根据按钮在窗口中的 Y 坐标位置从极光色带中采样。极光色带是一个从顶部紫蓝渐变到底部青绿的垂直渐变色谱。按钮的 Y 坐标映射到色带上的对应位置，采样出该位置的 RGB 颜色值，作为按钮环境色的基色。

此外，环境色还叠加了一个呼吸调制效果。呼吸周期约为 4 秒，使用正弦波函数调制颜色的亮度，使按钮的颜色在微妙的范围内周期性地变亮和变暗，模拟极光带流动的视觉效果。这种细节处理使得按钮看起来像是沉浸在真实的极光环境中，而非简单地叠加了一个静态渐变。

### 6.3 iOS Q 弹释放反馈

按钮释放时的回弹动画采用了 iOS 风格的二次回弹曲线。当用户释放按钮时，按钮首先向按下方向继续压缩一小段距离（模拟惯性），然后回弹到比原始大小稍大的尺寸（过冲），再回弹到比原始大小稍小的尺寸（二次过冲），最后稳定在原始大小。整个回弹过程持续约 600ms，通过自定义的 AuroraCustomEasing 曲线实现。

在 WPF 中，这种复杂的回弹曲线通过继承 IEasingFunction 接口实现自定义缓动函数，然后在 Storyboard 的 DoubleAnimation 中直接引用。与 V1.3.x 中使用多个 Timer 分段实现相比，WPF 的实现更简洁、更精确，且不依赖 Timer 的精度。

### 6.4 微噪点磨砂纹理

按钮表面叠加了一层微噪点磨砂纹理，与毛玻璃系统的噪点纹理使用相同的生成算法和共享机制。噪点纹理通过 Lazy 模式在所有按钮之间共享同一个实例，确保零额外内存开销。

## 7. 动画系统

V1.4.27.0 的动画系统代表了整个项目在动画领域最深刻的架构变革。从 V1.3.x 的 WinForms Timer 驱动分段动画，升级为 Storyboard 窗口级动画与 CompositionTarget.Rendering 帧级动画的双驱动架构。

### 7.1 四阶段视图切换

视图切换动画分为四个精确编排的阶段，每个阶段的时长经过精确计算以确保视觉流畅。

第一阶段，按钮退场。当前视图中的所有按钮执行退出动画，按从下到上的顺序依次淡出和下沉，每个按钮之间有 40ms 的延迟差，形成波纹退场效果。第一阶段总时长取决于按钮数量，通常为 200ms 到 350ms。

第二阶段，骨架退场。当前视图的窗口背景、面板框架等骨架元素执行统一的淡出和缩小动画，时长 200ms。

第三阶段，骨架入场。目标视图的窗口背景、面板框架等骨架元素执行统一的淡入和放大动画，时长 250ms。骨架入场比骨架退场稍长，因为入场动画需要更多的时间让用户感知新视图的空间结构。

第四阶段，按钮入场。目标视图中的所有按钮执行入场动画，按从上到下的顺序依次淡入和上浮，每个按钮之间同样有 40ms 的延迟差，形成波纹入场效果。第四阶段总时长取决于按钮数量，通常为 200ms 到 350ms。

整个四阶段的总时长约在 850ms 到 1150ms 之间，与人类视觉感知的自然过渡时间窗口一致。

### 7.2 双驱动架构

双驱动架构是 V1.4.27.0 动画系统的核心设计决策。

Storyboard 驱动窗口级动画，包括视图切换、按钮状态转换、控制台滚动等。Storyboard 的优势在于其声明式定义、自动时间线管理、内置缓动函数支持，以及 WPF 框架对 Storyboard 的原生优化。

CompositionTarget.Rendering 驱动帧级动画，包括星空粒子更新、极光色带流动、呼吸调制等。帧级动画需要在每一帧中更新属性，这是 Storyboard 无法高效处理的场景。CompositionTarget.Rendering 在每次垂直同步信号时触发，配合帧率归一化算法，确保帧级动画在不同刷新率下保持一致的感知速度。

两种驱动方式通过 AnimationService 统一协调。AnimationService 确保同一个属性不会被两种驱动方式同时修改，避免动画冲突。在视图切换期间，AnimationService 会临时暂停 CompositionTarget.Rendering 驱动的帧级动画，优先保证视图切换动画的流畅性。

### 7.3 UWP 风格缓动曲线

V1.4.27.0 实现了完整的 UWP 风格缓动曲线库，包括 CubicEase、QuadraticEase、QuarticEase、QuinticEase、SineEase、CircleEase、BackEase、ElasticEase、BounceEase 和 PowerEase 共 10 种缓动函数。每种缓动函数都支持 EaseIn、EaseOut 和 EaseInOut 三种模式，通过 UwpEasingCurves 类统一暴露。

这些缓动曲线在 UWP 和 Windows 11 原生应用中广泛使用，引入它们使得 Aurora 的动画质感与 Windows 原生应用保持一致，消除了之前 GDI+ 动画中"非线性但不够自然"的视觉感受。

## 8. 控制台

AuroraConsoleBox 是主界面底部的日志输出控制台，在 V1.4.27.0 中进行了全面的 WPF 重构。

### 8.1 批量行刷新

V1.3.x 的控制台每收到一条日志就立即刷新显示，当日志输出频率较高时，频繁的 UI 更新导致界面卡顿。V1.4.27.0 引入了批量行刷新机制：日志行首先进入一个缓冲区，320ms 的批次延迟后，将缓冲区中累积的所有日志一行性输出到 UI。

在这 320ms 的批次延迟期间，系统还会执行 260ms 的平滑滚动动画。控制台的滚动条不是直接跳转到新位置，而是以 UWP 风格的缓动曲线平滑滚动到底部，避免突兀的跳跃感。

### 8.2 UWP 风格文本滑入动画

每条新日志行出现时，不是简单地直接显示，而是执行一个从右侧滑入的动画。文本从右侧 20 像素偏移处开始，在 200ms 内滑入到正常位置，同时透明度从 0 过渡到 100%。多条日志行同时出现时，每行有 30ms 的延迟差，形成逐行滑入的层叠效果。

### 8.3 毛玻璃背景与自定义滚动条

控制台背景采用 AuroraGlassMaterial 的毛玻璃效果，与主界面保持视觉一致性。滚动条完全自定义绘制，使用极光主题色作为滑块颜色，轨道为半透明玻璃材质。自定义滚动条在鼠标悬停时展开到正常宽度，鼠标离开后收缩到细条模式，兼顾了美观性和可用性。

## 9. 性能优化

V1.4.27.0 的性能优化策略围绕"减少 CPU 绘制负载、降低 GC 压力、避免不必要的渲染操作"三个核心目标展开。

### 9.1 四级性能分级

系统提供四个性能等级，用户可根据硬件配置自由选择。

| 等级 | 名称 | 目标帧率 | 模糊质量 | 粒子数量 | 动效复杂度 | 适用场景 |
|------|------|----------|----------|----------|------------|----------|
| 1 | Eco | 30fps | 低（8px 半径） | 50% | 简化 | 低配机器、虚拟机 |
| 2 | Balanced | 60fps | 中（16px 半径） | 75% | 标准 | 普通办公电脑 |
| 3 | Performance | 60fps | 高（24px 半径） | 100% | 完整 | 高性能笔记本 |
| 4 | Extreme | 120fps | 最高（32px 半径） | 150% | 完整 | 高端台式机、游戏本 |

在 Eco 模式下，模糊背景的捕获频率降低到 15fps，模糊半径缩小到 8px，星空粒子数量减少 50%，部分非关键按钮动效被简化。在 Extreme 模式下，所有效果以最高质量运行，模糊捕获频率提升到 60fps，星空粒子数量增加到基准的 150%。

### 9.2 笔刷缓存池化

如毛玻璃系统中所述，所有常用画刷在首次创建后被冻结并缓存。这项优化在频繁渲染的场景中效果显著——一个包含 10 个按钮的视图，每帧可能涉及 50 次以上的画刷引用，缓存池化将这些操作从"每次分配新对象"变为"从字典查找已冻结对象"，完全消除了对应的 GC 分配。

### 9.3 模糊背景节流

模糊背景的 RenderTargetBitmap 捕获操作被限制在 30fps，在无毛玻璃控件可见时完全跳过。这项优化在 Balance 和 Eco 模式下还会进一步降低捕获频率，确保模糊效果不会成为性能瓶颈。

### 9.4 共享噪点纹理

所有毛玻璃控件和按钮共享同一个 128×128 噪点纹理实例。如果 20 个控件各自独立生成噪点纹理，将浪费约 1.3MB 的纹理内存。共享机制将这部分内存开销降低到约 65KB。

### 9.5 帧率归一化

帧率归一化不仅解决了不同刷新率显示器上的动画速度不一致问题，还防止了高刷新率显示器上的不必要渲染。在 120Hz 显示器上，如果不进行归一化，动画速度会翻倍，导致用户感知到的动画过于急促，同时也浪费了 GPU 资源。

## 10. 安全增强

V1.4.27.0 在 V1.3.26.7 安全机制的基础上进行了增强，将部分 PowerShell 实现的安全功能迁移到 C# 编译代码中，提高了安全机制的可靠性和抗篡改能力。

### 10.1 C# IntegrityGuardService

V1.3.x 的完整性校验在 PowerShell 脚本中实现，存在被篡改的理论风险——攻击者如果能够修改 PowerShell 脚本，就可以同时修改校验逻辑。V1.4.27.0 将 IntegrityGuardService 实现在预编译的 C# DLL 中，校验逻辑编译为 IL 代码，篡改难度显著提高。该服务在应用启动时自动执行文件完整性校验，验证所有核心 DLL 和脚本文件的哈希值是否与预期一致。

### 10.2 RSA 令牌验证

RSA 令牌验证机制在 V1.4.27.0 中得到保留和增强。令牌包含四个部分：nonce、timestamp、hashPayload 和 signature。验证流程包括 RSA 签名验证、时间窗口检查（60 秒有效期）和哈希匹配。验证逻辑在 C# 中实现，利用 .NET Framework 内置的 RSACryptoServiceProvider 提供硬件级别的密钥保护。

### 10.3 AES-256-CBC 提权令牌

UAC 提权场景下的信任链恢复通过 AES-256-CBC 加密的提权令牌实现。令牌包含 nonce、timestamp 和 payload，通过 PBKDF2 派生密钥。新进程通过命令行参数 `-ElevationTokenPath` 接收令牌文件路径，解密后验证 payload 中包含的脚本路径和哈希列表。令牌有效期为 120 秒，比正常令牌窗口稍长以容纳 UAC 提权操作的时间。

### 10.4 Watchdog 监控服务

WatchdogService 监控应用的运行状态，检测异常退出、进程挂起和资源泄漏。如果检测到主进程异常终止，WatchdogService 会触发安全清理流程，清除敏感的环境变量、临时文件和会话状态。Watchdog 与主进程之间通过心跳机制保持通信，心跳间隔为 5 秒，超时阈值为 15 秒。

### 10.5 进程退出安全清理

V1.4.27.0 实现了三层退出清理机制。第一层，所有实现了 IDisposable 接口的 Service 在应用正常退出时被依次调用 Dispose 方法。第二层，AppDomain.ProcessExit 事件注册的处理器在进程退出时强制清理所有资源。第三层，WeakReference 追踪所有未显式释放的资源，在 GC 回收时触发最终清理。三层机制确保无论应用以何种方式退出，敏感资源都能被正确清理。

## 11. 兼容性说明

V1.4.27.0 在设计之初就将兼容性作为核心约束，确保现有用户和脚本能够无缝迁移。

### 11.1 PowerShell 5.1 兼容

所有 C# 代码使用 C# 5.0 语言版本编译，确保编译后的 DLL 可以在 PowerShell 5.1 的 CLR 4.0 环境中加载。C# 5.0 是 PowerShell 5.1 支持的最高语言版本，选择此版本确保了最大程度的兼容性。

### 11.2 脚本接口兼容

V1.4.27.0 保持了与 V1.3.x 系列完全相同的 PowerShell 脚本接口。所有公开的函数签名、参数名称、参数类型和返回值类型保持不变。现有的 PowerShell 脚本引擎无需任何修改即可在新架构上运行。UI 层的变更对脚本引擎完全透明。

### 11.3 syncHash 同步机制兼容

syncHash 是 V1.3.x 中用于 PowerShell Runspace 与 UI 线程之间通信的核心同步机制。V1.4.27.0 保持了 syncHash 的数据结构和通信协议完全不变，确保现有的通信代码无需修改。

### 11.4 命令行参数兼容

所有命令行参数保持与 V1.3.x 系列一致，包括 `-GUI_Mode`、`-syncHash`、`-LanguageResource`、`-ElevationTokenPath`、`-LaunchedByExe` 等。用户和外部启动器无需修改任何命令行参数。

## 12. 已知限制

V1.4.27.0 作为架构升级版本，存在以下已知限制，这些限制主要源于技术栈的底层约束。

### 12.1 .NET Framework 4.8+

WPF 的完整功能集需要 .NET Framework 4.8 或更高版本。V1.4.27.0 在 .NET Framework 4.8 上开发和测试，在较早的 .NET Framework 版本上可能存在兼容性问题。Windows 10 和 Windows 11 默认包含 .NET Framework 4.8，但 Windows 7 和 Windows 8.1 需要手动安装。

### 12.2 Windows 10+

WPF 的 DirectX 渲染管线依赖 Windows Display Driver Model 2.0，该模型在 Windows 10 中首次引入。Windows 7 和 Windows 8.1 虽然支持 WPF，但部分渲染特性（如高性能模糊效果）可能回退到软件渲染模式，导致性能下降。官方推荐运行环境为 Windows 10 1809 或更高版本。

### 12.3 GDI+ 特有效果的近似处理

V1.3.x 中使用的部分 GDI+ 特有效果在 WPF 中没有直接等价物。例如，PathGradientBrush 的复杂多色渐变在 WPF 中通过多个 RadialGradientBrush 叠加近似实现。这种近似在视觉效果上非常接近原版，但在极端情况下（如渐变色差极大的场景）可能存在细微差异。
